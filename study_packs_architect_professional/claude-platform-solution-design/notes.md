## Key Concepts

| Concept | Study Notes |
|---|---|
| Four design decisions before building | (1) What part of the work should Claude own? (2) What shape is the work (augmented call, workflow, agent)? (3) What reference architecture are you committing to? (4) Where does the work interact with Claude (entry point, model, context strategy)? |
| Four properties of generative AI | Next-token prediction, Knowledge, Working memory, Steerability. Each is a capability/limitation pair, not a flaw to "fix" — an architect designs around it. |
| Next-token prediction (capability/limit) | Good at pattern-rich tasks (summarizing, reformatting, explaining established concepts). Fails on precision specifics (names, dates, citations, statistics) — can be fluently wrong. Mitigation: citations, uncertainty signaling, generator-verifier loops, route factual lookups to tools/authoritative sources. |
| Knowledge (capability/limit) | Reliable on common, recent, consistently-trained topics. Unreliable on rare, niche, contested, or fast-changing topics — presents stale info with the same confident tone as established facts. Mitigation: web search, RAG, tool use, MCP to make an external system the source of truth instead of the model. |
| Working memory (capability/limit) | Anything fitting the active context window is usable; once content falls outside the window it's inaccessible. Two distinct edge errors: an oversized request (rejected before generation) vs. a mid-generation ceiling hit (truncated output). Mitigation: progressive context loading, chunking, front-loading critical info, projects, cross-turn summarization. |
| Oversized request errors | If a prompt exceeds the model's token limit: API returns 400 `invalid_request_error` ("prompt is too long"). If the raw request body exceeds the API's byte limit: API returns 413 `request_too_large`. Both are rejected before generation ever starts. |
| Mid-generation context ceiling | When a prompt fits but generation runs into the window ceiling, the response returns with a `model_context_window_exceeded` stop reason and truncated output. Check the `usage` field on every response, and the token-counting API, before sending. |
| Steerability (capability/limit) | Good at short, concrete, verifiable instructions with defined formats and clear roles. Fails on abstract/ambiguous instructions, long reasoning chains, precise numerical/logical computation — may follow the letter of an instruction while drifting from its intent. Mitigation: system prompts, structured outputs, code execution for logical precision; restate the goal explicitly alongside the instruction. |
| Design consequences of the four properties | Non-determinism → why evaluation frameworks exist (you cannot certify behavior observed only once). Context as finite resource → why context strategy is a design decision. Confidence is not validity → why human-in-the-loop placement and verification are architectural choices. Knowledge/capability boundaries → why retrieval, tools, and MCP exist. |
| Demo-is-not-evidence-of-determinism failure | A team saw a demo run cleanly five times and treated the model as deterministic, shipping a financial reconciliation pipeline with no checks. In week two, re-processing the same statement produced a different categorization — non-determinism surfaced only by chance when an analyst re-ran a batch. |
| Three architecture layers | Entry Points, Build-Time Interfaces, Delivery Routes. Not alternatives — every deployment involves all three, and confusing them is the most common source of muddled architecture conversations. |
| Entry Points | What a person/system directly interacts with; decide who can talk to Claude and how. Examples: Claude.ai (web/mobile/desktop), Claude Code, a custom app built on the API. Chosen for the user and the work. |
| Build-Time Interfaces | How an engineer programs against Claude; the layer the partner's code is written to. Examples: the direct API, SDKs, MCP, the Agent SDK. Chosen for the engineering team and integration. |
| Delivery Routes | Where API traffic terminates; whose infrastructure the request runs on. Examples: Anthropic directly, AWS Bedrock, GCP Vertex AI, Microsoft Foundry. Chosen for the partner's cloud commitments and compliance posture. |
| Collapsed-layers failure | A retail banking proposal put Claude Code (an engineering entry point) in front of a non-engineering audience, reasoning "it's all Claude." Claude Code is built for developers running a terminal, not bank branch staff — the entry point was wrong even though the underlying model was the same. |
| Seven AI primitives | Tools (Act), MCP (Connect), Subagents (Isolate/Parallelize), Hooks (Guarantee), Skills (Package a procedure), Agent Teams (Coordinate peers), Dynamic Workflows (Compose at runtime). Patterns (augmented call, workflow, agent) are assemblies of these primitives, not separate categories. |
| Tools | What lets the model take an action or fetch a result from your code — a function the model can call. |
| MCP (primitive definition) | A protocol for exposing a set of tools so multiple Claude clients can reach the same entry points. |
| Subagents | Hand a scoped sub-task to a separate context so work runs in isolation or in parallel. |
| Hooks | Deterministic code that fires on defined events to enforce a rule the model cannot skip. |
| Skills (primitive definition) | A versioned, reusable unit (instructions plus optional scripts) that packages a repeatable procedure. |
| Agent Teams | Multiple agents working as coordinated peers, each owning part of a larger goal — extends the older single-agent vocabulary. |
| Dynamic Workflows | Assemble the steps of a workflow at runtime rather than fixing them in advance — extends the older fixed-workflow vocabulary. |
| Shared-vocabulary failure | In a review, "we'll use an agent" meant five different architectures to five people (single tool-using model, multi-step workflow, subagent team, Claude Code, chatbot) — the design conversation stalled 20 minutes on vocabulary alone. |
| Three solution owners | What Claude does (language understanding, summarization, planning, drafting, tool-mediated action), what existing systems do (anything the partner already paid to make reliable: order-status service, policy engine, rules table, DB of record), what humans do (judgment calls, exception paths, approvals). |
| Delegation and its three justification tests | Decomposition produces a delegation map: for each step, decide not just whether Claude *can* do it but whether Claude *should own* it. Justify via Reversibility (can a wrong call be undone?), Stakes (what does a wrong call cost?), Accountability (who must answer for it?). Delegation is the first of the four AI Fluency competencies. |
| Decomposition framing | Ask "where do the four properties argue for Claude over the system that already does this right?" — not "where can Claude help?" Over-assigning to Claude is the most common and most expensive early mistake. |
| Claims-triage decomposition example | Read the claim → Claude (pattern-rich language work, constrainable output). Decide priority → existing rule engine (deterministic business rule, not language work). Look up policy coverage → existing/live system via tool call or MCP (knowledge boundary + high stakes). Draft the adjuster email → Claude; send the email → existing system; approve above a value threshold → human. |
| Deterministic-drift failure (Watch Out) | A partner's SQL-based rule ("claims over £5,000 need senior adjuster") was replaced with a Claude prompt to "keep it simple." Of 14,000 claims, 41 misrouted — all cases where the amount was embedded in prose ("around five thousand pounds") rather than a clean number; the model treated it as a loose estimate. Caught by an audit three months later, not by monitoring, because there was no test suite and no logging captures in-request model choices the way a broken SQL check would be caught. |
| Lesson of deterministic drift | A rule that must be right every time was handed to a system that is right most of the time. The gap is invisible in demos/early testing (which show clean cases) and surfaces only in an audit. Deterministic business rules stay in deterministic systems. |
| Three architecture patterns | Augmented LLM, Workflow, Agent — positioned on two axes: predictability of the path through the work, and model autonomy granted. |
| Augmented LLM | High predictability, low autonomy: one bounded model call (optionally with tool use, retrieval, extended thinking). Control flow never branches on what the model decides. Use when the task is well-defined and verifiable, with no reason to split into multiple steps. |
| Workflow | Predictable shape; bounded model judgment inside each step. You decompose the task into named steps and orchestrate them in your own code — loggable, testable, reasoned about like other software. Use when error cost is real, observability matters, and steps can be determined in advance. |
| Agent | High autonomy, low predictability: the model determines its own sequence of steps toward a goal; control flow lives in the model, not your code. Use only when the path cannot be enumerated in advance and the cost of an unexpected/inconsistent output is acceptable and recoverable. Claude Code is the production-proven example. Production agents need constrained tool entry points, per-turn budgets, explicit permissions, and stopping criteria — not optional. |
| Workflow sub-pattern: Chaining | Step 2 takes step 1's output as input, sequential/linear. Use when the task decomposes into stages with clear handoffs (extract → classify → summarize). Example: contract review pipeline (extract obligations → classify risk → draft memo). |
| Workflow sub-pattern: Routing | A classifier (often Claude) decides which downstream path to take. Use when inputs vary in kind and need different handling. Example: support ticket triage routes billing to an account-data index, technical issues to product docs, escalations to a human queue. |
| Workflow sub-pattern: Parallelization | Multiple model calls run concurrently; results aggregated/voted on. Use when sub-tasks are independent. Example: 12 supplier contracts reviewed simultaneously, results aggregated into one risk report. |
| Workflow sub-pattern: Evaluator-optimizer | One call drafts, a second call evaluates against criteria and requests revision; loop repeats until quality criterion met or retry limit hit. Use when quality is verifiable but a single attempt isn't reliable enough (code-gen against a test suite, strict-schema extraction). Example: complaint-response draft graded against a rubric, rewritten until it passes or hits a retry limit. |
| Combining sub-patterns | Most production workflows combine more than one sub-pattern. Pick the simplest pattern meeting error-tolerance and observability requirements; escalate complexity only when production data shows the simpler pattern falling short. |
| Five-factor pattern-selection framework | Walk factors in sequence — Predictability, Error cost, Observability, Latency budget, Cost — asking whether each rules out a pattern. The first factor that rules one out is the deciding one. |
| Five factors compared across patterns | Predictability: Augmented LLM=low(single bounded task)/Workflow=low(you wrote the path)/Agent=high(trajectory unpredictable by design). Error cost: Augmented=medium/Workflow=low(deterministic guards between steps)/Agent=high. Observability: Augmented=medium/Workflow=low(steps log like code)/Agent=high(tooling isn't built to alert on trajectories). Latency: Augmented=low(fastest)/Workflow=medium(additive)/Agent=high(budget for worst case, not median). Cost: Augmented=low(fewest tokens)/Workflow=medium(scales with steps)/Agent=high(iterative reasoning, retries, growing context — poorly bounded agents are often the most expensive pattern). |
| Prompting-before-fine-tuning progression | (1) Optimize the prompt — most reliability problems are prompt problems. (2) Add tool use or retrieval. (3) Move to a stronger pattern (e.g., evaluator-optimizer) if quality still isn't there. (4) Only then consider fine-tuning. |
| When fine-tuning has a place | Very high volume where inference cost is the real constraint; latency-critical where a smaller specialized model beats a prompted general one; output must follow a consistent format that prompting hasn't reliably solved. Fine-tuning locks you to a fixed model version — treat it as a last step, not a quick fix. Availability is limited and varies by model/delivery route; confirm with the Anthropic account team. |
| Skills-based architecture as packaging | Three packaging options on a spectrum: prompt-only (instructions alone), direct tool use (model calls functions in your code), Skills-based (versioned, reusable, governed unit bundling instructions + scripts). Reach for a Skill when the same procedure runs repeatedly, must be distributed across teams/products, or must be versioned and governed. |
| Delegation lens applied to pattern choice | Ask whether the chosen pattern grants Claude appropriate or excessive decision authority for the risk profile. An autonomous agent is right only when the stakes and reversibility of its actions justify the autonomy granted. |
| Agent-not-chosen-because-uncertain trap | Agents are often chosen because a task *feels* open-ended, not because the steps genuinely can't be enumerated. Feeling uncertain about structure ≠ a task whose steps can't be determined in advance; if you could write the steps in code, use a workflow. |
| Flexibility-vs-non-determinism failure (Watch Out) | A team chose an agent for "flexibility," then spent months bolting on guardrail tools until they'd rebuilt a workflow inside the agent loop minus the logging. At month 3, traces showed only four actual path shapes — enumerable from day one, i.e., a router + four chains. |
| Agent autonomy as a compliance risk | When an auditor asked which step approved a disbursement, the team could only point to a model turn (no discrete auditable step) — and the model version had silently rolled forward two weeks earlier with no re-validation checkpoint. The version-pinning gap would exist under any pattern; the "no discrete step" gap is specific to choosing agent over workflow. |
| Multi-agent system roles | Orchestrator: owns the goal, decomposes work, decides delegation, synthesizes results — never does sub-task work itself. Subagents: own scoped sub-tasks, each in its own context, return a result. |
| Three things to design (not assume) in multi-agent systems | How work is decomposed into sub-tasks; how each subagent's result is structured for the orchestrator to combine; how the orchestrator resolves conflicts/gaps in returned results. |
| Fan-out pattern | The most common multi-agent shape: orchestrator splits a large work item (400-file codebase audit, 200-doc corpus, 50-rule regulatory filing) into independent units, dispatches one subagent per unit (parallel where independent), synthesizes results into one deliverable. Wins: clean per-unit context sizing, concurrent execution. |
| Multi-agent failure recoverability asymmetry | Subagent failure = usually recoverable (orchestrator can retry, re-route, or drop-and-flag while the rest proceeds). Orchestrator failure = usually NOT recoverable (loses the goal/synthesis thread → whole run fails, partial subagent work stranded). Design for this: make subagent work idempotent/retryable; protect orchestrator state. |
| Multi-agent failure-response table | Malformed/empty subagent result → validate, retry/re-route, record the gap (don't fail the run). Conflicting subagent results → give the orchestrator an explicit conflict-resolution rule or escalate to a human. Orchestrator loses goal/state → protect state, checkpoint progress so a failed run can resume, not restart. Fragmented traces → propagate a shared trace ID across orchestrator and subagents. |
| Human-in-the-loop checkpoint placement | A checkpoint is a gate pausing execution for review, positioned by the risk/reversibility of the action about to be taken. Place a gate before any irreversible or high-stakes autonomous action; sample lower-stakes actions rather than gating every one. This is part of orchestration design, not bolted on afterward. |
| Fan-out drop failure (Watch Out) | A compliance team fanned a 50-section vendor contract review to 50 subagents; the orchestrator reported "48 sections reviewed, 3 flagged" and it was circulated as complete. Two subagents had actually failed (one timeout, one unparseable scanned page) and returned nothing — the orchestrator only counted results it received, with no rule requiring result count to equal dispatched-unit count. |
| Why fan-out drop broke | Three compounding gaps: (1) no coverage check at synthesis, (2) a recoverable failure (timeout/empty parse) had nothing watching the boundary so it went unretried and unflagged, (3) the fluent, well-formed summary masked the gap — a multi-agent system fails most dangerously when a confident-looking summary is built over unfinished work. Fix: synthesis must assert results-returned == units-dispatched or flag the difference before anyone reads the summary. |
| Reference architectures — role | Once a pattern gives you the shape, a reference architecture gives you the wiring: a documented, industry-proven way to wire an LLM application together for a recurring class of problem. Reference architectures are references, not blueprints to adhere to rigidly — adapt the shape that fits. |
| Common reference architectures named | Agent; Retrieval-augmented generation (RAG); Document processing pipeline (uses evaluator-optimizer sub-pattern); Customer-service/ticket triage (uses routing sub-pattern); Coding agent (agentic exploration with deterministic edit/test/review steps). |
| Composing multiple reference architectures | Real problems often sit at the boundary of two architectures (e.g., a routing workflow handing certain intents to an agentic investigation loop). Reach for a second pattern only when the two parts of the problem break in different ways worth managing separately — not because you haven't decided what problem you're solving (that's a deferred design decision, not a composition). |
| Retrieval-vs-tool-call mistake | The most common reference-architecture mistake: using retrieval where a tool call belongs. Symptoms: stale chunks, results shifting with each index refresh, answers contradicting the live database. A better embedding model or shorter refresh interval will NOT fix this — call the system that owns the live state directly instead. |
| Retrieval-vs-tool-call trace example | Customer asks "Where's my order?" Two retrieved chunks disagree (one says shipped, one says still processing) because the index holds text snapshots from different points in time, not current state. The model picked the higher-similarity chunk and answered confidently wrong; the order had actually shipped, been returned to depot for a damaged label, and awaited re-dispatch — a state that existed in neither chunk. A live order-status tool existed in the partner's API and was never called. RAG is right for stable reference material (docs, policy text, manuals); it breaks for live/transactional state because an index captures what was true when written, not what's true now. |
| Composed-architecture cost/complexity/risk | Cost: composing two reference architectures roughly doubles maintained surface area — pick one when in doubt. Complexity: each reference architecture carries its own eval contract; you need separate eval sets per architecture, not one eval set for the composed system, since a system healthy at the top level can mask component failures. Risk: retrieval-on-live-state produces stale-but-confident answers with normal latency and no errors — detection cost is high because nothing signals a problem until a user notices reality doesn't match the answer. |
| Context engineering (broad skill) | Deciding which mechanism is responsible for getting each kind of data in front of the model (retrieval, tool call, system prompt, working memory) — the retrieval-vs-tool-call failure is one instance of getting this decision wrong. |
| Chunking approaches (RAG) | Fixed-size (uniform spans + overlap; homogeneous/unstructured text, simplest to operate); Semantic (split on meaning/topic boundaries; prose needing self-contained chunks, reduces mid-idea cuts); Hierarchical (preserve sections/subsections, retrieve at the level that fits; structured docs like contracts/manuals/policies where section context carries meaning). Chosen by the structure of the source material, not a default size. |
| Indexing strategies (RAG) | Dense/embeddings (semantic similarity; paraphrase/intent/concept-matching queries); Sparse/keyword e.g. BM25 (exact terms, identifiers, codes, names); Hybrid (both, combined; the common production case, recovers exact-match hits dense retrieval misses). Chosen by the query pattern, not the corpus alone. |
| Reciprocal rank fusion | The standard, low-tuning way to merge two ranked lists (dense + sparse) into one: each result is scored by its rank in each list, and the combined score favors items ranking well in both. Combining dense and sparse results is a design decision with a known, defensible default. |
| RAG pipeline three-way trade-off | Retrieval quality (does the right chunk come back?), Latency (how long retrieval adds per request), Maintenance (pipeline cost to keep correct as the corpus grows/changes). Smaller chunks + hybrid indexing raise quality and latency together; larger chunks + dense-only lower latency/maintenance but miss exact-match queries. No universally right point — state the trade-off as a defensible choice for this corpus and these queries. |
| RAG exercise worked example | 4,000-doc professional-services corpus: structured section-numbered contracts → hierarchical chunking (section context carries meaning, supports exact-target lookup like "find the termination clause"). Long-form project write-ups → semantic chunking (self-contained chunks for broad synthesis). Structured methodology handbook → hierarchical chunking (concept lookup by section). Full-corpus indexing → hybrid (dense for concept/methodology questions, sparse for exact clause/identifier lookups), trading some latency/maintenance for coverage across all three query types. |
| Four distinct context-related terms | Context window (the model's active attention space; resets between calls unless the app manages continuity). Retrieval (fetched external knowledge at query time; augments, does not replace, the context window — model only sees what the retriever surfaces). Persistent application state (owned by your system — order status, user records, balances; model has no inherent access, requires a tool call). Summaries/memory layers (application-managed continuity across turns/sessions; the model has no native memory between calls — anything persisting does so because your app stored and re-passed it; an architectural choice, not a model capability). |
| Model selection: start with Sonnet | Claude model family: Opus (most capable, demanding reasoning/advanced coding/research synthesis where Sonnet misses the quality bar), Sonnet (default starting point), Haiku (move down only when an eval set confirms the quality tradeoff is acceptable). Model tier changes must be measured via an eval set, never reflexive. |
| Context-window sizing / the "working-memory cliff" | Attention works fully inside the window and not at all outside it — an abrupt edge, not a gradual degradation. Measured in tokens (chars-per-token ratio is only a rough illustration; measure via the `usage` field on every response). Everything entering the window — system prompt, conversation history, retrieved docs, tool outputs, model responses — is counted and billed. Practical rule: budget for the largest realistic conversation + retrieved context + system prompt + working scratch + margin for growth — the window is a ceiling, not a target. |
| Context strategy spectrum | Monolithic (load everything into one prompt; works for bounded/predictable input sizes, but hits the working-memory cliff as context accumulates silently) ↔ Progressive (stage context, retrieve just-in-time, summarize across turns, load only what's needed next — where most production workloads belong). Two more strategies sit between: Retrieval/RAG (fetch relevant chunks at query time) and Compaction (periodically summarize/compress accumulated context). |
| Combining context strategies (coding-agent worked example) | Session start = monolithic prefix (small, stable, ideal for prompt caching). Active work = progressive recent state (latest tool-call additions). Discovery = just-in-time retrieval (search codebase for files not initially loaded). Context filling = compaction (summarize "what we tried and learned," drop verbatim tool outputs). No single strategy alone carries the workload — monolithic alone hits the limit, progressive alone can't surface unloaded code, retrieval alone loses the trajectory, compaction alone has nothing to compact until the others build it up. |
| Context strategy vs. context sizing | Two separate decisions that interact but don't determine each other — treating them as one is where most context-management designs go wrong. |
| Extended thinking mechanics | A per-request capability: the model reasons in a separate thinking-token block before the final answer. On Opus 4.6+/Sonnet 4.6+/Sonnet 5, adaptive thinking with the `effort` parameter is the recommended control (set reasoning effort, not a token budget); it's the only thinking mode on Claude Fable 5. The older manual `budget_tokens` is deprecated on 4.6 and removed on Sonnet 5 (returns a 400 error there). Thinking tokens bill as output tokens at standard rate and add latency; when not engaged, none are generated or billed. The API may return a summarized reasoning trace, but billing is for tokens actually consumed, not the summary's length. |
| Extended thinking decision rule | It's a cost/latency tradeoff, not a free quality boost. Run evals WITHOUT it first; only enable it if accuracy still misses the bar after prompt work, and the case for turning it on must come from a measured accuracy gap — not the assumption "it can't hurt." |
| Gating a model swap with evals | Any model change is a behavior change — treat it as a code deployment/release. Minimum requirements: (1) a curated test set with known-good outputs covering the real work distribution, (2) a grading function (model-graded rubric or programmatic), (3) a delta threshold set in advance (before running the eval — setting it after means you're writing acceptance criteria after the build, not setting a standard). |
| Sonnet-to-Haiku downgrade worked case | Document-intelligence pipeline on Sonnet 6 months in, over budget. Built a 250-doc eval set stratified by document type. Sonnet scored 0.94 avg, Haiku 0.86 avg, with two document types at 0.71/0.74 — below a pre-set 0.85 rollback threshold. Full migration rejected; salvage move: route the two weak document types to Sonnet via the existing classifier, route the rest to Haiku. Cost dropped materially with no regression on the hard types. Key lesson: the rollback criterion set BEFORE the data arrived is what let the team avoid negotiating with itself and surface a partial-migration option a single overall score would have hidden. |
| Opus-everywhere failure (Watch Out) | Team defaulted every call in a stack to Opus during build ("use the best model," no eval set required, no choice to defend). 90 days post-launch: cost at 7x modeled figure, median latency 2.3s vs. an 800ms target, CSAT unchanged. Contributing factors: no model-tier decision was ever written into the architecture (so the implicit default became the most expensive option); cost was reviewed only monthly, so the gap surfaced weeks after launch; extended thinking was left on for a routing classifier that needed no reasoning at all. Fix: built an eval set retroactively, routed the classifier to Haiku and mid-pipeline summarization to Sonnet (both confirmed no regression), kept Opus only on final response composition (the one place the eval justified it). Result: cost down 71%, latency down to 940ms, CSAT unchanged. |
| Opus-everywhere lesson | Not choosing a model tier is equivalent to choosing the most expensive one — the absence of a deliberate choice is not neutral. An eval set is the only thing that makes a tier decision defensible in the design conversation, not just a release gate. |
| System-prompt architecture for enterprise reuse | An enterprise system prompt (hundreds of requests/day) is a different artifact from a one-off chat prompt: it needs a clear role/scope statement, explicit constraints (must-not / must-always), and an output contract naming the response shape. At scale, ambiguity is a defect multiplied across every request. |
| Templates | A system prompt with parameterized slots (per-request variable content) plus fixed scaffolding around them. Design goal: fixed scaffolding carries the consistency/safety guarantees so filling a slot cannot accidentally remove a constraint — the safe path becomes the default path. |
| Description (AI Fluency competency applied to prompts) | Description = precisely stating scope (what's in/out of bounds), format (the exact output contract), and constraints (rules that must never be violated). Separates a prompt that works in a demo from one that holds in production. |
| Underspecification | Where a prompt is silent, the model improvises — differently each time — which is exactly the non-determinism you don't want in a reused asset. Diagnose by asking, for each requirement the output must meet, whether the prompt actually states it or merely hopes for it; fix by making the implicit explicit (restate the goal, name the format, bound the constraints). An underspecified guardrail is worse than a missing one — it creates the appearance of a control without the substance. |
| Prompt technique selection by complexity | Zero-shot (instruction only; well-specified tasks the model already handles reliably — the default to try first), Few-shot (a handful of input/output examples; when the desired format or judgment is easier to show than describe), Chain-of-thought (reason step by step before answering; multi-step reasoning, arithmetic-like logic, or tasks where the path matters). Progression is deliberate: start zero-shot, add examples only if needed, add explicit reasoning only if the task structure demands it — each step adds tokens/latency. |
| Technique-selection checkpoint examples | Ticket classification into 5 fixed categories → zero-shot (well-specified, model already handles it). Extracting date/vendor/amount from receipts with wildly varying layout → few-shot (format/judgment easier to show than describe). Multi-condition contract-liability determination → chain-of-thought (multi-step reasoning where the path matters). Summarizing a 400-word description into 2 sentences → zero-shot (well-specified, simple task). |
| Behavioral differences across models | The same prompt does not behave identically across model tiers/generations — a more capable model may need less scaffolding (fewer examples, less explicit step-by-step) for the same quality; a prompt tuned for one model is a starting point for another, not a finished artifact. This is why a model swap is gated with an eval: the prompt-model pairing is what you're actually shipping. |
| Avoiding bias in prompt construction | Leading phrasing, unbalanced few-shot examples (showing only one kind of case), and baked-in assumptions all steer output in easy-to-miss ways. Discipline: phrase neutrally, balance examples across cases the system will actually see, and check whether the prompt presumes an answer it should be eliciting. Bias is invisible in any single output and only shows up in aggregate. |
| Prompt caching mechanics | Cache breakpoints, content ordering, TTL selection, and knowing when write overhead isn't worth it are all architect-level design decisions. The cache matches on a stable prefix — putting per-request/dynamic content ahead of the large fixed instruction block means the prefix changes every request and the cache never hits. Fix: order fixed content first, dynamic content last. |
| Modular prompt library vs. Skill (reuse decision) | Prompt library = shared fragments/templates engineers assemble in their own code; lightweight governance, engineers own the fragments; fits an assembled/often-tweaked prompt used within one codebase/team. Skill = formal, versioned, self-contained unit (SKILL.md + optional scripts + version management) that travels as one governed artifact; fits a stable procedure run the same way every time, distributed across teams/products, needing versioning/approval/rollback. |
| Reusable prompt asset exercise (support-reply example) | Three design decisions to make explicit: (1) where the stable prefix ends and per-request content begins (breakpoint placement, for caching); (2) how to enforce a guardrail (e.g., "never promise a refund/timeline") structurally via an output contract constraint, not just as a stated instruction; (3) whether to ship as a template (assembled/tweaked per use) or a Skill (stable, versioned, cross-team procedure). |
| Three sequential consumption decisions | Which entry point fits the work → which build-time interface suits the team → which delivery route fits the partner's cloud commitments. Order matters; getting them in the right sequence prevents the most common architecture mistakes. |
| API vs. SDK | Same entry point from Claude's perspective, different ergonomics. The SDK is an opinionated wrapper over the API — language-native types, streaming/tool-use boilerplate handled, supports Python/TypeScript/Java/Go/Ruby/C#/PHP. SDK is the default for most teams; drop to raw HTTP only when a freshly shipped API feature hasn't reached the SDK yet. |
| MCP vs. API tool use | Different layers, not alternatives — an MCP server exposes tools that any MCP-aware client can call using API tool use under the hood. Pick MCP when one tool entry point must be reachable from multiple Claude clients; pick raw API tool use when the tools live inside one product only. |
| Claude Agent SDK | The managed runtime that runs the agent loop (the same one powering Claude Code): the model picks a tool, runs it, sees the result, keeps going until done or a stop condition fires. Distinct from the "Anthropic SDK" (a convenience wrapper over the API with no agent loop) — the term "SDK" is ambiguous in practice, so name which one you mean. Decision: one request/one response → API/SDK. Reusable tools across clients → MCP. Claude acting across multiple turns inside the partner's own product → Agent SDK. |
| Claude Code customization vs. governance layers | Shaping layers (what the agent knows/does): CLAUDE.md, Skills, subagents, MCP. Governing layers (what the agent is allowed to touch): Hooks, permission boundaries, approval flows, sandboxing, restricted execution. Each layer is independent, composable, and applied at a different point in the agent's execution — getting the shaping/governing split right is what makes an agent both useful and safe in production. |
| CSP delivery routes decision rule | The model behaves identically on every route — the decision is about what the partner has already committed to (cloud contract, identity system, region, procurement), not technical capability. If the partner has a long-term AWS/GCP/Azure contract, use Bedrock/Vertex/Foundry respectively (spend falls under the existing agreement, identity system works as-is). Use the direct Anthropic API when the partner has no strong cloud preference, wants new features immediately, or prefers spend to stay with Anthropic directly. Trade-off: CSP-mediated routes (Bedrock/Vertex/Foundry) tend to lag the first-party API on new features by weeks or longer. |
| What changes vs. doesn't across delivery routes | Unchanged: the model itself, prompting, evaluation strategy, tool use, context-window behavior all transfer. Changed: model identifiers/version strings, regional availability, and CSP-side wrapper features (Bedrock inference profiles, Foundry model deployments, Vertex Model Garden access controls) that the architect needs to know exist even if the partner's engineering team owns the implementation. |
| Skills as an integration mechanism | Not only packaging — a Skill can be attached to a request via the `container.skills` parameter, published/versioned through the `/v1/skills` endpoint, and managed under version control like any deployed asset. Skills require the Code Execution Tool to run, so the integration pattern carries a sandboxed-execution dependency. Weigh a versioned Skill alongside MCP and direct tool use when deciding how a reusable procedure reaches Claude across entry points. |
| Regulated-industry constraints eliminate options first | When a partner is subject to attorney-client privilege, HIPAA, GDPR, FedRAMP, or internal data-residency policy, those constraints rule entry points in or out BEFORE cost, ergonomics, or build effort enter the conversation. Claude.ai (the consumer-grade product) is hit most often — it wasn't designed to satisfy every enterprise data-handling requirement out of the box. The API/SDK routed through a partner-approved gateway with logging, retention, and identity controls in the partner's own infrastructure survives most regulated reviews. Name the governing constraint before preferences. |
| Claude Code Misused failure (Watch Out) | A regional bank's proposed "operations assistant": Claude Code on branch laptops with a per-branch CLAUDE.md, MCP servers for customer DB/appointments/policy corpus, subagents running compliance checks per interaction. Three failure mechanisms: (1) entry point chosen before the user was named — branch staff don't run terminals, so Claude Code (an engineering entry point) was mismatched to a banking workflow; (2) MCP carried forward as a default integration layer with no reusability need — no other Claude clients existed in the bank to justify the protocol overhead; (3) compliance (the highest-consequence path) was assigned to subagents, the entry point with the weakest deterministic guarantees, inverting the pattern — the work needing the most code-level certainty ran furthest from it. Right answer: a custom web app calling the API directly, compliance in deterministic server-side code, SSO-authenticated UI fit to a banking workflow, tool calls audited at the server boundary. |
| Entry-point selection worked scenarios (checkpoint) | Non-technical ops team + approved docs → Claude.ai + Project (audience tradeoff: ready-made entry point, not a build-time interface). Bank loan-officer assistant needing programmatic core-banking access on AWS → Bedrock (integration depth + existing AWS agreement). Law firm needing firm-owned audit trail for privileged docs → direct API/SDK behind the firm's own app + gateway (governance/control: firm must own the audit trail end-to-end). Non-technical warehouse floor staff on shared tablets → Claude.ai + Project (audience: ready-made interface, no training needed) — NOT Claude Code (a terminal tool, wrong audience despite running on a device staff can touch). Healthcare network with an existing AWS BAA already confirmed to cover Bedrock → Bedrock (governance/control: the existing BAA eliminates compliance risk before any other tradeoff applies — not "regulatory residency", and not renegotiating a separate BAA when one is already in place). High-frequency trading firm on GCP needing 400ms trade commentary → Vertex AI (latency: staying inside the firm's existing GCP environment minimizes round-trip; not "fastest feature releases" or "managed infrastructure" claims about other routes). |
| Cumulative assembly worked example (law firm contract review) | Brief: 180-lawyer firm, senior associates spend 12-18 hrs/week on contract review, 35-page average contracts, iManage storage, CIO-approved private LLM gateway, attorney-client privilege excludes consumer-grade tools, target 60% time reduction with senior associate as final reviewer. The four options test each of five decisions (entry point, pattern, work split, model/context strategy, human-in-the-loop) — correct answer (Option D) uses: direct API/SDK behind SSO + approved gateway (privilege excludes Claude.ai); a parallelized workflow with an evaluator pass enforcing a strict schema (not an open-ended agent — the steps ARE enumerable: extract, classify, redline); Claude does extraction/classification/draft redlines while the playbook stays a versioned source of truth in firm systems retrieved per clause (not loaded in full every call, and not left to agent discretion); Sonnet by default with progressive context, extended thinking enabled per clause only where an eval justifies it (not blanket Opus "for maximum accuracy" with no eval backing); senior associate signs off on every output with low-confidence clauses flagged (human-in-the-loop matches the brief's requirement that the associate remain final reviewer). Wrong options fail on: Option A (Claude.ai violates the privilege/gateway requirement), Option B (loading the full playbook into the system prompt every call instead of versioned per-clause retrieval — burns tokens and risks staleness), Option C (an open-ended agent for enumerable steps, plus Opus on every call with no eval justification — violates both the pattern-selection and model-selection decision rules). |
| Recap takeaway 1 | Decomposition is the move that comes before architecture — split into what Claude/existing systems/humans handle, driven by how the model behaves on each piece. Skipping this forces Claude into work another system would do cheaper, or asks it to operate without context a human would have. |
| Recap takeaway 2 | Choosing a pattern is choosing how much autonomy to grant — augmented LLM / workflow / agent is a spectrum from "Claude assists one step" to "Claude plans the whole sequence." The five factors (predictability, error cost, observability, latency, cost) decide; when error cost is the binding constraint, error cost picks the pattern — the tightest constraint decides. |
| Recap takeaway 3 | Reach for tested reference architectures before inventing your own: Agent, RAG, Document processing pipeline (evaluator-optimizer), Routing, Coding agent. Combine them only when different parts of the system break differently; pick one when still uncertain what the system needs to handle. The most common mistake is using retrieval as a substitute for live state. |
| Recap takeaway 4 | Choosing a model: start with Sonnet and treat every swap as a release, gated by an eval set defining "better" and a rollback criterion set before the swap. Same principle applies to context: progressive context holds up better over a long-lived deployment than monolithic context that grows until it breaks. |
| Recap takeaway 5 | Pick the entry point by the work it has to do, not by what's already on the shelf. Claude.ai / direct API / SDK / Claude Code / MCP each carry a different core tradeoff (setup speed vs. control depth, prebuilt UI vs. custom integration, tool breadth vs. focus). The right recommendation is the one where you can name the tradeoff out loud — which is also what tells you later when to switch. |
| Glossary — selected exam-relevant terms | Adaptive thinking (effort-based extended-thinking control on newer models); Authoritative (a source whose data is treated as the current source of truth, as opposed to the model's parametric knowledge); Corpus (the body of documents a retrieval system indexes); Deterministic rule (a business rule that must be correct every time, owned by code/a system, not a probabilistic model); Live state (current, system-of-record data that changes independently of any index — the concept behind the retrieval-vs-tool-call failure); Parametric knowledge (what the model learned during training, as opposed to retrieved or tool-fetched data); Shippable (a system ready for production release, implying it has passed its eval gate). |

## Decision Rules

- Before assigning any step of a request to Claude, ask "where do the four properties argue for Claude over the system that already does this right?" — not "where can Claude help?"
- If a business rule must be correct every time (a deterministic rule the business already relies on), keep it in the deterministic system (SQL check, rules engine) — do not fold it into a model prompt, even if that looks simpler.
- If the answer must reflect current, live, or transactional state (order status, account balance, live coverage), route it through a tool call / API / MCP server to the system of record — never through retrieval over an index.
- If the path through the work can be enumerated in advance and written in code, use a Workflow, not an Agent, even if the task "feels" open-ended.
- Choose Agent only when the path genuinely cannot be enumerated in advance AND the cost of an unexpected/inconsistent output is acceptable and recoverable; always bound it with constrained tool entry points, per-turn budgets, explicit permissions, and stopping criteria.
- Walk the five-factor sequence (predictability, error cost, observability, latency budget, cost) in order; stop at the first factor that rules out a pattern.
- Before recommending fine-tuning, work through prompting → tool use/retrieval → a stronger pattern (e.g., evaluator-optimizer); only reach for fine-tuning after that sequence fails, or when volume/latency/format-consistency genuinely require it.
- Reach for a Skill (not a one-off prompt) when a procedure runs repeatedly, must be distributed across teams/products, or must be versioned and governed.
- In multi-agent design, always add a synthesis-time coverage check: results returned must equal units dispatched, or the run must flag the discrepancy before anyone reads the output.
- Place a human-in-the-loop gate before any irreversible or high-stakes action a subagent (or agent) would otherwise take autonomously; sample lower-stakes actions instead of gating every one.
- Protect orchestrator state (checkpoint progress) because orchestrator failure is usually unrecoverable, while subagent failure usually is recoverable (retry/re-route/flag-and-continue).
- Choose an entry point for the user and the work, a build-time interface for the engineering team, and a delivery route for the partner's cloud/compliance posture — treat these as three separate stakeholder conversations, never one.
- Check governance and regulated-industry constraints on entry point / delivery route before evaluating any cost or latency tradeoff — some routes are ruled out entirely before other tradeoffs even apply.
- Reach for a second reference architecture only when two parts of the problem fail in genuinely different ways worth managing separately — not as a substitute for deciding what problem you are solving.
- Use citations, uncertainty signaling, and generator-verifier loops for output requiring precision on names/dates/citations/statistics; do not rely on the model's fluent output alone.
- For rare, niche, contested, or fast-changing knowledge, make an external system (web search, RAG, tool use, MCP) the source of truth instead of the model's parametric knowledge.
- Check the `usage` field / token-counting API before sending a request that may be near the context window limit, and design progressive loading/chunking/summarization for extended work rather than hoping it fits.
- Choose chunking by the structure of the source material (fixed-size for homogeneous unstructured text, semantic for prose needing self-contained chunks, hierarchical for structured/sectioned documents) — never by a default chunk size.
- Choose indexing by the query pattern (dense for paraphrase/concept queries, sparse/BM25 for exact terms/IDs/codes, hybrid with reciprocal rank fusion for the common mixed-query production case).
- Start model selection at Sonnet; move to Opus only when an eval set shows Sonnet misses the quality bar, and move to Haiku only when an eval set confirms the quality tradeoff is acceptable — never move a tier reflexively.
- Do not budget the full context window — budget for the largest realistic conversation plus retrieved context plus system prompt plus working scratch plus growth margin; the window is a ceiling, not a target.
- Treat context strategy (monolithic/progressive/retrieval/compaction) and context sizing (how much of the window to use) as two separate, interacting decisions — do not conflate them.
- Run evals without extended thinking first; enable it only when accuracy still misses the bar after prompt work, justified by a measured accuracy gap, not the assumption "it can't hurt."
- Gate every model swap with a curated eval set, a grading function, and a delta/rollback threshold set BEFORE the eval runs, not after.
- Write a model-tier decision into the architecture explicitly for every step — an absent decision silently defaults to the most expensive model.
- Design enterprise system prompts with an explicit role/scope statement, explicit must-not/must-always constraints, and a named output contract — ambiguity in a reused prompt is a defect multiplied across every request.
- For caching to work, order the stable/fixed instruction content first and per-request/dynamic content last — the cache matches on a stable prefix.
- Reach for a Skill (not a prompt library) when a procedure must be distributed across teams/products or needs versioning, approval, and rollback; use a prompt library when it's an assembled, often-tweaked prompt within one codebase/team.
- Decide entry point, then build-time interface, then delivery route, in that sequence — and check regulated-industry constraints (privilege, HIPAA, GDPR, FedRAMP, data residency) before cost, ergonomics, or build effort, since they can eliminate options outright.
- Choose a CSP delivery route (Bedrock/Vertex/Foundry) based on the partner's existing cloud contract and identity system, not technical capability (the model behaves the same on every route); use the direct API when there's no strong cloud preference or the partner wants new features immediately.
- Assign the highest-consequence path (e.g., compliance) to the component with the strongest deterministic guarantees (server-side code), never to the entry point or primitive with the weakest ones (e.g., subagents).

## Anti-Patterns

- Treating a demo that ran cleanly a handful of times as proof of deterministic behavior, then shipping with no evaluation framework or checks.
- Folding a deterministic business rule (a threshold, a policy check) into a Claude prompt "to keep it simple," instead of leaving it in the system that already enforces it reliably.
- Putting an engineering entry point (e.g., Claude Code) in front of a non-engineering audience because "it's all Claude" — collapsing entry points, build-time interfaces, and delivery routes into one undifferentiated concept.
- Reaching for an agent because a task "feels" open-ended rather than because its steps genuinely cannot be enumerated in advance — often rediscovered later as "we rebuilt a workflow inside the agent loop, minus the logging."
- Leaving a model version unpinned in a governed/compliance-relevant pipeline with no re-validation checkpoint when it rolls forward.
- Synthesizing a multi-agent result without a coverage check, so a dropped or failed subagent silently produces a confident-looking but incomplete answer.
- Using retrieval (RAG) to answer questions about live, transactional, or frequently-changing state instead of calling the system of record via a tool.
- Composing multiple reference architectures as a way to avoid deciding what problem you're actually solving, rather than because the problem's parts genuinely fail in different ways.
- Jumping straight to fine-tuning when the reliability problem is actually a prompt problem, or one that tool use/retrieval/a stronger pattern would solve first.
- Reaching for a heavier primitive (agent team, subagent fan-out) than the job requires, paying the extra latency/token/operational cost for no benefit.
- Assuming an agent's tool permissions are automatically scoped safely — the broader the tool permissions, the larger the space of untested action combinations.
- Skipping the eval-set-per-architecture discipline on a composed system, letting a healthy-looking top-level system mask a failing component underneath.
- Choosing chunk size or indexing strategy by a default/habit rather than by the corpus structure and the actual query patterns the system will see.
- Defaulting every call in a pipeline to the most capable model ("use the best model") to avoid building an eval set, deferring cost/latency discovery to a monthly bill review instead of design time.
- Leaving extended thinking enabled on a step (e.g., a routing classifier) that never needed reasoning, paying latency and token cost with no accuracy justification.
- Loading a full reference document (like a playbook) into the system prompt on every call instead of retrieving only the relevant slice, or leaving stable content that could be cached at the end of the prompt instead of the front.
- Copy-pasting the same prompt across teams without versioning it as a Skill, letting slightly different variants drift into inconsistent behavior.
- Reaching for Claude Code or MCP by default because "the last project used them," rather than because the current work and audience actually need them.
- Assigning a high-consequence, must-be-certain path (like compliance) to the entry point or primitive with the weakest deterministic guarantees (e.g., subagents) instead of deterministic server-side code.
- Picking an entry point (like Claude.ai) for a regulated workload before checking whether privilege/HIPAA/GDPR/FedRAMP/residency requirements rule it out.
- Setting a model-swap rollback/delta threshold after seeing the eval results instead of before running the eval.

## Scenario Traps

- Trap: "It ran clean five times in the demo, so it's deterministic." Better: a demo is not evidence of determinism; non-determinism is a property of the model regardless of whether the architecture acknowledges it.
- Trap: "This threshold rule is easy enough for Claude to just check in the prompt." Better: a rule the business is counting on to be right every time belongs in a deterministic system, tested and owned by a human — not left to a model that's right "most of the time."
- Trap: "It's all Claude, so any entry point works for any audience." Better: entry points, build-time interfaces, and delivery routes are three distinct decisions for three distinct stakeholders; the wrong entry point is a common, avoidable, and expensive error.
- Trap: "We're not sure how to structure this, so let's use an agent for flexibility." Better: uncertainty about structure is not the same as a task whose steps can't be enumerated — mine what the actual paths look like before choosing autonomy over a workflow.
- Trap: "Agents are inherently more expensive than workflows." Better: cost is driven by context accumulated and model calls made, not the pattern label — a poorly designed workflow can cost more than a well-designed agent.
- Trap: "The summary says 48 of 50 reviewed with no errors, so it's complete." Better: a fluent, complete-looking synthesis can mask silently dropped or failed subagent units; verify coverage (results returned == units dispatched), don't assume it.
- Trap: "RAG worked great on the docs use case, so let's use it for order status too." Better: RAG is for stable reference material between index refreshes; live/transactional state needs a direct tool call to the system of record, or the answers will be stale but confidently wrong.
- Trap: "A better embedding model or a shorter refresh interval will fix the stale/contradictory RAG answers." Better: that's a retrieval-vs-tool-call architecture mistake, not a retrieval-quality problem — no embedding tuning fixes retrieving text snapshots of state that changes faster than the index refreshes.
- Trap: "We should combine two reference architectures to cover all our bases." Better: only compose patterns when the two problem parts fail in genuinely different ways worth managing separately; otherwise you're deferring a design decision, not applying a pattern.
- Trap: "One eval set covers the whole composed system." Better: each reference architecture in a composed system carries its own eval contract and needs its own eval set.
- Trap: "The orchestrator failed, but we can just retry the whole multi-agent run like a subagent failure." Better: orchestrator failure is usually unrecoverable (goal/synthesis state lost); protect and checkpoint orchestrator state so a failed run can resume rather than restart from scratch.
- Trap: "Use the best available model everywhere — it's the safe, defensible choice for the demo." Better: not choosing a model tier IS choosing the most expensive one; an eval set, not the model's reputation, is what makes a tier choice defensible, and per-step tiering usually cuts cost sharply with no quality loss.
- Trap: "A bigger context window means we don't need a context strategy." Better: context strategy (how context reaches the model) and context sizing (how much of the window to use) are separate decisions — a bigger window doesn't fix a monolithic strategy that silently accumulates until it hits the cliff.
- Trap: "Enable extended thinking, it can't hurt accuracy." Better: it's a billed, latency-adding pass — turn it on only when evals show a measured accuracy gap that prompt work alone didn't close.
- Trap: "It's all Claude Code / it's all MCP, so it's the right choice for this team too." Better: entry-point choice should follow the user and the work, not what the last project happened to use — Claude Code is a terminal tool for engineers, and MCP earns its place only when a tool must be reused across multiple clients.
- Trap: "Bedrock/Vertex/Foundry vs. the direct API is a technical-capability decision." Better: the model behaves identically across delivery routes — the decision is about the partner's existing cloud contract, identity system, and procurement, not capability.
- Trap: "The firm already has an existing BAA/agreement covering this configuration, but let's still evaluate other routes on their technical merits." Better: when an existing agreement already covers the compliance requirement, that eliminates the compliance risk before any other tradeoff (cost, latency, ergonomics) even applies — don't relitigate it as a technical question.
- Trap: "The task is open-ended, so give the agent full discretion over the whole document/process." Better: even inside an agent-friendly problem, check whether individual steps (like enforcing an output schema) should still be pinned down with a workflow sub-pattern (like evaluator-optimizer) rather than left to full agent autonomy.
- Trap: "Cache the prompt by putting the important per-request data first so the model sees it clearly." Better: for caching to hit, order stable/fixed content first and per-request content last — the cache matches on a stable prefix, and leading with dynamic content defeats it entirely.

## Memorization Cues

- Four properties: Next-token prediction, Knowledge, Working memory, Steerability — capability + limitation + mitigation, each.
- Three layers: Entry Points (who/how), Build-Time Interfaces (engineer's code), Delivery Routes (whose infrastructure).
- Seven primitives and their one-word jobs: Tools=Act, MCP=Connect, Subagents=Isolate/Parallelize, Hooks=Guarantee, Skills=Package a procedure, Agent Teams=Coordinate peers, Dynamic Workflows=Compose at runtime.
- Three owners: Claude / Existing systems / Human — decided via Reversibility, Stakes, Accountability.
- Three patterns on two axes (predictability x autonomy): Augmented LLM = high predictability, low autonomy. Workflow = predictable shape, bounded judgment per step. Agent = high autonomy, low predictability.
- Four workflow sub-patterns: Chaining (sequential handoffs), Routing (classify then dispatch), Parallelization (independent, concurrent, aggregated), Evaluator-optimizer (generate, grade, revise loop).
- Five-factor sequence for pattern choice: Predictability → Error cost → Observability → Latency budget → Cost. First one that rules out a pattern wins.
- Fine-tuning order of operations: Prompt → Tool use/retrieval → Stronger pattern → Fine-tuning (last resort).
- Multi-agent asymmetry: Subagent fails = recoverable. Orchestrator fails = usually not recoverable.
- Multi-agent silent-failure fix: results returned MUST equal units dispatched, or flag it.
- Reference architecture rule of thumb: retrieval = stable reference material; tool call = live/transactional state.
- Cost/Complexity/Risk framing recurs on every teaching screen — use it to structure any tradeoff answer.
- RAG chunking: Fixed=uniform spans, Semantic=meaning boundaries, Hierarchical=document structure. RAG indexing: Dense=meaning/paraphrase, Sparse=exact terms/IDs, Hybrid=both (merged via reciprocal rank fusion).
- Model tiers: Opus=demanding reasoning (move up only on eval evidence), Sonnet=default starting point, Haiku=move down only on eval evidence.
- Context strategy spectrum: Monolithic ↔ Progressive, with Retrieval and Compaction as two more strategies in between — production systems layer all four.
- Model swap = release: eval set + grading function + pre-set rollback threshold, always in that order (threshold BEFORE results).
- Prompt technique ladder: Zero-shot → Few-shot → Chain-of-thought — use the lightest one that meets the requirement.
- Caching rule: fixed content first, dynamic content last, or the cache never hits.
- Reuse packaging: Prompt library = lightweight, one team, often-tweaked. Skill = versioned, governed, cross-team, stable procedure.
- Three sequential consumption decisions: Entry point (user/work) → Build-time interface (engineering team) → Delivery route (cloud/compliance commitments).
- Regulated constraints (privilege, HIPAA, GDPR, FedRAMP, residency) eliminate entry-point options BEFORE cost/ergonomics/build-effort tradeoffs are even considered.
- Claude Code layers: Shaping (CLAUDE.md, Skills, subagents, MCP) vs. Governing (Hooks, permission boundaries, approval flows, sandboxing).
