## Key Concepts

| Concept | Study Notes |
|---|---|
| Diagnose-before-reprompt rule | A failing prompt has one of four missing pieces: output constraint (wrong shape), system prompt (content/scope drift), few-shot examples (hallucinated structure), or a constraint covering an untested variant (breaks on edge case). Reword only after naming which piece is missing. |
| Six-pass anti-pattern | A real trace of a classification prompt getting longer across 6 passes without fixing the root cause: pass 4 is a diagnostic failure (added description instead of constraint), pass 5 is an engineering failure (verbose prompt induces 2,000+ char verbose output and latency regression with no accuracy gain). If 3 re-prompts fail in a row, stop and diagnose instead of adding more text. |
| System prompts | The persistent, session-wide behavioral contract: role, output format, and rules that must not change between turns. |
| XML tags for input/instruction separation | Wrap inputs (code, docs, examples) in descriptive tags like `<my_code>`/`<docs>` so Claude does not conflate instructions with data. Tag names do not need to be "official" — descriptive names work best. |
| Few-shot examples | One correct `<sample_input>`/`<ideal_output>` pair shows the exact structure instead of describing it; pull examples from your highest-scoring eval outputs rather than writing from scratch. |
| Output constraints | The last line of defense before the parser: specify field names, types, length limits, preamble policy, and behavior when data is absent. |
| Structured outputs (JSON outputs) | Set `output_config.format` with `type: json_schema`; constrained decoding only allows tokens valid against the schema, so a schema-violating response cannot be generated. Use when Claude itself must produce the structured payload. |
| Strict tool use | Set `strict: true` on a tool definition; Claude's arguments are validated against the input schema before your code runs. Use in agentic loops to prevent malformed arguments from crashing a function. |
| Structured output costs | First request on a new schema is slower (grammar compilation, cached 24 hours from last use); input tokens rise (API injects a format-description system prompt); a guaranteed schema is not a guaranteed success (`stop_reason: refusal` or `stop_reason: max_tokens` can still occur); incompatible with message prefilling. |
| Extended thinking mechanics | Thinking content returns as a `thinking` block ahead of the answer; on newest models it is omitted by default unless requested. Effort is adaptive (tuned via an effort setting), not a fixed token budget. |
| `budget_tokens` deprecation | The old fixed-budget parameter is deprecated and returns a 400 error on newest model generations; effort-based control replaced it. |
| Thinking-block carry-back rule | Every thinking block (including redacted/encrypted ones) must be sent back to the API completely unchanged on the next turn of a tool-use loop. Each block carries a signature; editing, summarizing, or dropping it breaks the signature and the API rejects the request. This is a structural requirement, not a prompting choice. |
| When to enable extended thinking | Enable for multi-step reasoning and agentic multi-tool planning (budget for the planning step). Leave off for mechanical/lookup tasks like classification, format conversion, or field extraction — a bare prompt with an output constraint is cheaper and equally accurate. |
| Tool-use loop mechanics | Claude does not execute tools itself — it emits a `tool_use` block naming the tool and arguments; your application code executes it and returns a `tool_result`; Claude continues. Six steps: define schema, send message, receive `tool_use` block, execute tool, return result, Claude continues. |
| Message block types | `text` (assistant prose, may co-occur with tool_use — preserve the full content array when appending to history), `tool_use` (assistant: name/id/input), `tool_result` (user role even though app-generated: role marks sender not author; matching `tool_use_id`, optional `is_error`), `thinking` (assistant, extended thinking only, must round-trip unchanged). |
| tool_use/tool_result ID pairing invariant | Every `tool_use` block from an assistant turn must be answered by a `tool_result` with the exact matching ID in the immediately following user turn, or the API rejects the request with a validation error. Matters especially when a turn has multiple parallel tool calls that may return out of order. |
| Tool schema anatomy | Three parts: `name` (specific, e.g. `get_account_balance` not `get_data`), `description` (must state when to use AND when not to use — vague descriptions like "use this to find information" cause wrong-tool selection), `input_schema` (JSON Schema; mark fields required only when the call is meaningless without them). |
| Sequential vs parallel tool calls | Use sequential calls when one tool's output feeds the next call's input. Models default to parallel tool_use blocks in one turn when calls are independent; set `disable_parallel_tool_use` to force exactly one call per turn. |
| Required vs optional schema fields | Over-marking fields as required forces Claude to fabricate values it doesn't have. Leave true-optional fields out of the required array and give them defaults in the function signature so Claude can omit unknowns instead of guessing. |
| Description-length guidance | 3-4 sentences: what the tool does, when to reach for it, what it returns, and valid input examples. Too short causes guessing; too long buries the actual trigger conditions. |
| Overlapping-parameter disambiguation | When two tools take similar-looking parameters, Claude routes primarily on name + description, so add explicit domain/trigger language and mutual exclusion conditions to each tool's description rather than relying on the input schema to differentiate them. |
| "Wrong tool" failure pattern and fix | Two tools whose descriptions both read like "use this to find information" become indistinguishable to Claude regardless of differing schemas. Fix: add an explicit exclusion condition to EACH tool's description (e.g. "Do not call this if the answer is already in context" / "Only use this if X was already called for the same query"). If descriptions still can't be cleanly separated, merge the tools into one with a `type` parameter. |
| MCP (Model Context Protocol) | A standardized layer that moves tool definitions/execution to dedicated servers; loop mechanics are unchanged, only the setup step differs (client sends `ListToolsRequest`, tool list is indistinguishable from manually authored tools from Claude's perspective). |
| MCP context cost | Every connected MCP server adds its tool definitions to the context window even when unused in the current turn — register only actively-used servers. |
| API MCP Connector config | Declared via an `mcp_toolset` object in the tools array; `default_config` applies to all tools on the server, overridable per-tool via `configs` keyed by tool name; `defer_loading` (boolean) delays loading a tool's definition until the model actually needs it; `enabled` (boolean) turns individual tools on/off. Requires the `mcp-client-2025-11-20` beta header. |
| MCP transports | Local servers use stdio (subprocess); remote servers use Streamable HTTP (POST client→server, optional GET-based SSE for server-initiated messages); the older SSE-only transport is deprecated. The API MCP Connector only supports HTTP-exposed remote servers. |
| MCP vs manual tools vs both | Use MCP when a well-maintained server already covers the needed operations. Write manually when no server covers the use case or you need precise description-quality control. Use both to get breadth from connected servers plus precision from description-tuning discipline and per-tool allowlisting. |
| Streaming event sequence | `message_start` (empty content, initial usage) → `content_block_start` (new block opens at an index) → `content_block_delta` (incremental text/JSON/thinking fragment) → `content_block_stop` (block at that index is complete) → `message_delta` (top-level `stop_reason` + final usage) → `message_stop` (stream complete). |
| Streaming assembly discipline | Never act on a partial block — a tool_use block's input JSON string is not parseable until `content_block_stop`. Only append the assembled assistant turn to conversation history after `message_stop`, with every block fully closed. |
| Stream interruption handling | A dropped connection or timeout can end the event series before `message_stop`. Treat the turn as provisional until `message_stop` arrives; on interruption, discard the partial turn entirely (do not save it to history) and retry from the last complete turn. |
| Stream-end vs message-complete | The core lesson of the streaming Watch Out: a stream ending is not the same as a message completing. Committing a turn to history without gating on `message_stop` can silently persist a truncated tool_use block that only errors on the NEXT request (the retry), misleading debugging toward the schema instead of the stream handler. |
| Model tiers | Fable (Anthropic's most capable model, for complex reasoning/advanced coding/research synthesis/sophisticated agentic workflows), Opus (demanding work above Sonnet's envelope), Sonnet (balanced default for most production workloads), Haiku (speed/cost efficiency within its capability envelope). Move up or down only based on eval results, not assumption. |
| Context window is not free | The window holds the system prompt, full conversation history, and all tool results. A request that already exceeds the window is rejected before generation; a request that fits but hits the ceiling mid-generation returns partial output with `stop_reason: model_context_window_exceeded`. Neither path silently truncates old content — the application must manage trimming itself. |
| Dev-vs-prod context gap | Production tool outputs commonly run 3-5x longer than development fixtures and production sessions run more turns, so a session that stays comfortably within budget in testing can hit the ceiling many turns earlier in production (e.g., turn 8 instead of turn 50). |
| Four context-budget strategies | Pruning (jump back to an earlier message, drop what came after — loses work done after the rewind point), Compaction (summarize history into a condensed version — loses details not captured in the summary; `/compact` in Claude Code, server-side compaction beta in the API, or manual summarization), Clearing (start a fresh, empty context — loses all session context; `/clear` in Claude Code or a new API session), Subagent Handoffs (spawn a subagent in an isolated context window that returns only a summary — loses visibility into how the subagent reached its conclusion). |
| Compaction summarizer specificity | An under-specified summarizer prompt ("summarize the conversation so far") drops task-critical state. A well-specified one ("...preserving all file paths modified, all decisions made, and any errors encountered and their resolutions") produces a usable summary. Task-critical state loss from under-specified summarization is one of the most common sources of multi-session agent failures. |
| Prompt caching | Marks a stable prefix (long system prompt, large tool definition set, repeatedly-queried reference doc) with a `cache_control` field of type `ephemeral` on the last block to cache; up to 4 cache breakpoints per request; subsequent identical-prefix requests pay a fraction of the original cost. It is the highest-leverage cost reduction for multi-turn sessions with a stable system prompt/tool set. |
| `count_tokens` endpoint | Accepts the same request body as a Messages call and returns a token count without running inference — use in development to verify budget assumptions against real tool outputs, and in production to gate requests before they would error. |
| RAG failure points | Chunking (too small loses context, too large dilutes the match — sentence/section-based chunking with slight overlap is a reasonable default), Embedding match (semantic similarity can outrank an exact-term match — run lexical search alongside semantic when exact identifiers matter), Assembly (retrieved chunks must land in the prompt in the expected structure, or the model answers from memory instead of the retrieved text). |
| Fetch-once index vs agentic search | A pre-built index is inspectable and testable but costs infrastructure (build/store/sync/secure). Iterative agentic search costs more tokens/time per query but has no staleness or infra cost. Prefer an index for a stable corpus with simple lookups; prefer iterative search for a changing corpus or multi-step questions. |
| Workflow vs agent decision | Choose a workflow when you can enumerate the exact steps in code, error cost is real and step-level guardrails matter, inputs are well-constrained, and every execution follows the same sequence. Choose an agent when you can specify the goal and tools but not the exact path, non-determinism is acceptable within a constrained toolset, and inputs vary unpredictably. |
| Three agent wiring paths | Raw Messages API loop (your code owns the full loop, execution, retries, and exit conditions — full control, full maintenance burden), Agent SDK (the SDK runs the loop in your process; you still execute tools; `settingSources` controls whether CLAUDE.md/skills load — set it explicitly), Claude Managed Agents (Anthropic runs the loop and sandbox; your app sends events and consumes a stream; public beta, requires the `managed-agents-2026-04-01` beta header; sessions are stateful and server-stored, so NOT eligible for Zero Data Retention or a HIPAA BAA). |
| Four steps to wire an agent loop | Register tools, set a task-scoped system prompt (a broad prompt yields broader/less reliable routing), handle the tool-use loop (execute every call, return every result before the next assistant turn), and define explicit exit conditions (without them the agent keeps requesting tool calls beyond what the task needs). |
| Loop-wiring checklist | Tools registered (none referenced-but-unregistered), system prompt scoped to the task with no phantom or omitted tools, tool-use loop resolves every block from a turn together, at least one HITL insertion point defined, and exit conditions defined that do not depend on Claude volunteering to stop. |
| HITL insertion points | Before a destructive tool call (write/delete/send — high risk, irreversible), after a planning step (medium risk — a wrong plan can produce a wrong outcome even if every step executes correctly), and on unexpected output (error flag, empty result, out-of-bounds value — catches failures retry logic won't resolve). Guiding question: "What is the worst possible outcome if this step runs without a human check?" |
| Over-tooling vs under-tooling | Too many overlapping-description tools causes erratic routing; too few causes hallucinated paths or incomplete results. Over-tooling is the more common production problem — teams register "just in case" tools and selection quality degrades as the surface grows. Start minimal and add only when a specific gap is confirmed. |
| Regulated-data delivery routes | Attorney-client privilege rules out unauditable consumer surfaces (needs direct API/SDK with firm-side logging). HIPAA/PHI requires a BAA-covered configuration (direct API on a HIPAA-enabled org, or Bedrock/Vertex on a covered account) — a BAA does not cover Console, Workbench, betas, or consumer plans. GDPR/data residency requires a cloud-mediated route with the execution region pinned (the direct Anthropic API does not currently offer EU residency). FedRAMP/government work requires an authorized route: Claude for Government (FedRAMP High via Palantir Federal Cloud Service), Claude via Amazon Bedrock GovCloud (FedRAMP High, DoD IL4/5), or Claude via Vertex AI Assured Workloads (FedRAMP authorized) — Claude Enterprise on AWS Marketplace is NOT FedRAMP authorized. SOC 2 governs how systems are built/operated, not endpoint choice. |
| Memory scope options | In-context memory (state lives in the active conversation, zero retrieval overhead, but inflates every call and vanishes when the session clears — good for short sessions where nothing needs to survive a restart), External storage (written to a DB and read back at session start, adds retrieval latency, survives across sessions/users/instances), Summarized memory (a condensed version generated and injected at the next session start, lower token cost but drops any detail the summarizer didn't preserve), No persistent memory / stateless (nothing persists, zero overhead, correct for self-contained jobs that finish and close). |
| Memory scope is a design-time decision | The default trap is storing full history in the messages array: it works at first, then token cost scales with every turn until the agent hits a hard limit and stops responding. Refactoring to external storage afterward is mechanically simple but expensive in timing because it happens under production pressure with a deadline already in motion — deciding scope at design time avoids that. |
| Skills vs CLAUDE.md vs in-context instructions | A Skill (SKILL.md: frontmatter name/description + instructions) loads only when its description matches the current task — low context cost, ideal for task-specific expertise. CLAUDE.md loads into every session unconditionally in Claude Code CLI (in the Agent SDK, controlled by `settingSources`) — fixed overhead, ideal for always-on standards. In-context instructions persist only within a session and grow with it — ideal for short, one-off sessions. |
| Skills on the Messages API (beta) | Requires two beta headers together: `code-execution-2025-08-25` and `skills-2025-10-02`. Skills run inside the code execution container rather than the calling application's own environment, which affects tool/filesystem access. |
| Subagent Skill/permission inheritance | Subagents do NOT automatically inherit Skills from the parent session — they start with clean context (no automatic skill or conversation-history carryover), so a needed Skill must be explicitly listed in the subagent's configuration. Subagents DO inherit the parent session's permission context — permission scope is not reset at delegation. |
| Image token-cost formula | Claude views images in 28x28-pixel patches, one visual token per patch: visual tokens = ceil(width/28) x ceil(height/28). A 1000x1000px image is roughly 1,296 visual tokens. Ten high-resolution screenshots can approach the size of a detailed system prompt. Per-tier maximum resolution differs by model; oversized images are downscaled before the formula is applied. |
| Sending images (3 methods) | Inline base64 (full payload every request, best for one-off images), URL reference (no payload but requires a stable/public/reachable URL at request time), Files API (upload once, get a `file_id`, near-zero payload thereafter — best for assets reused across requests or turns; beta, not available on Bedrock/Vertex AI). |
| Sending PDFs | Block type is `document` (not `image`); source structure mirrors images (base64/URL/Files API `file_id`); no required `name` field; optional `title` (readable document name) and `context` (metadata) fields. All other mechanics (token cost, Files API reuse) match images. |
| Multimodal prompting still needs craft | A bare "describe this image" prompt produces shallow output for the same reason bare text prompts fail. Images carry ambiguity text doesn't (overlapping objects, depth/spatial relationships, partial occlusion) — the prompt should explicitly instruct how to handle each ambiguity type. |
| Message Batches API | Accepts up to 100,000 requests or 256 MB per batch (whichever comes first) in a single submission; you receive a `batch_id`, poll for completion, and download results. Per-token cost is lower than the synchronous API, but latency is non-deterministic and can take up to 24 hours (often much faster). Suited to offline pipelines, eval runs, and bulk data processing — not real-time interactions. |
| Batching anti-pattern | Looping over the synchronous API per item — even in smaller chunks — is not batching: the API still sees one request per item back-to-back and hits the same rate limits. The Message Batches API is a different submission model, not a smaller batch size. Batch results also return in arbitrary order, not submission order — use the `custom_id` field on each request to match results back to inputs. |
| Multimodal + batch combination risks | Two failure modes: misreading latency (using batch in a user-facing image flow passes tests but fails production because a user is waiting) and underestimating context cost (images/PDFs consume budget before text is processed; multi-large-image-per-request pipelines can blow past token limits at scale). |

## Decision Rules

- If a response comes back in the wrong shape, add an output constraint — do not reword the instruction.
- If content drifts or scope widens across turns, tighten or add a system prompt — the behavioral contract was too vague to hold.
- If the task is right but the structure is invented, add few-shot examples wrapped in XML tags.
- If output is clean on tested inputs but breaks on a variant, add a constraint or example naming that variant.
- If you've re-prompted 3+ times without improvement, stop adding text and diagnose which of the four techniques is missing.
- If the format must be machine-reliable, move enforcement into the API via structured outputs (`output_config.format` for the response, `strict: true` on a tool) rather than trusting prompt wording alone.
- If the task is multi-step reasoning or multi-tool planning, enable extended thinking and budget effort for the planning step; if it's classification/extraction/format conversion, leave thinking off.
- If you must carry a thinking block to the next turn, send it back completely unchanged (including redacted/encrypted blocks) — never edit, summarize, or drop it.
- If two tools are candidates for the same call and Claude keeps picking the wrong one, add an explicit exclusion condition to each tool's description before touching the schema types.
- If a subtask's output feeds the next tool call, call sequentially; if calls are independent, let Claude parallelize (or set `disable_parallel_tool_use` to force one at a time).
- If a well-maintained MCP server already covers your needed operations, connect it instead of writing tools by hand; if none does, or you need precise description control, write manually.
- If you receive a streamed response, do not act on or persist any block until `content_block_stop` (for that block) and `message_stop` (for the whole turn) have fired.
- If a stream is interrupted before `message_stop`, discard the partial turn and retry from the last complete turn — never append a partial assembly to history.
- If tool-selection quality degrades after a fixed number of turns, check context window fill before touching the schema.
- If a session's tool outputs are large or numerous, prune or compact before the ceiling, not after a failure appears.
- If the next task is unrelated to the current one, clear the session; if it's a continuation, compact or prune instead.
- If a subtask is self-contained and its intermediate reasoning would clutter the main context, hand it off to a subagent and keep only its summary.
- If you can enumerate the exact steps of a task in code, build a workflow; if you can only specify the goal and available tools, build an agent.
- If a tool call is destructive/irreversible (write, delete, send), insert a HITL checkpoint before it executes, decided at design time, not after an incident.
- If you're unsure whether to add another tool, don't — over-tooling (too many overlapping tools) degrades routing more often than under-tooling in production.
- If work involves PHI, EU data residency, or FedRAMP requirements, route through the compliant delivery path (BAA-covered config, region-pinned cloud-mediated route, or an authorized government route) rather than the default direct API endpoint.
- If a session must survive across days/users/instances, use external storage for memory; if a session is long but self-contained, in-context memory is fine; if each job is independent and terminates, use no persistent memory.
- If instructions are needed only for specific tasks, package them as a Skill (loads on demand); if they must apply to every session unconditionally, put them in CLAUDE.md.
- If a subagent needs a Skill, list it explicitly in the subagent's configuration — it will not inherit Skills automatically (though it does inherit permission scope).
- If sending an image or PDF, estimate its token cost with the patch formula before building the pipeline, and choose inline base64 for one-off assets, the Files API for reused assets, and the Message Batches API for high-volume offline workloads.
- If a workload is high-volume and not time-sensitive (nightly jobs, eval runs), use the Message Batches API instead of looping the synchronous API — looping is not batching and hits the same rate limits.

## Anti-Patterns

- Adding words to a prompt without diagnosing which structural technique (system prompt, XML tags, few-shot, output constraint) is actually missing — the six-pass classification trace shows this producing a slower, more verbose, still-broken prompt.
- Writing tool descriptions that only say what a tool does ("use this to find information") without saying when NOT to use it, causing indistinguishable routing between overlapping tools.
- Stripping or summarizing thinking blocks before sending them back to the API to "save context" — this breaks signature validation on the next turn; the real fix for context bloat is context engineering, not mutating thinking blocks.
- Appending a streamed assistant turn to conversation history as soon as the read loop ends, instead of gating the append on `message_stop` — silently persists a truncated tool_use block that only errors on the next (retry) request.
- Assuming development fixtures represent production data size — production tool outputs commonly run 3-5x longer, filling the context window many turns earlier than testing suggested.
- Holding all agent memory in-context by default because it's the simplest thing to write, then discovering under production pressure that token cost scales with every turn until the agent stops responding.
- Treating a chunked loop over the synchronous API as "batching" — it is still one request per item and hits the same rate limits as the unchunked version; only the Message Batches API is actually asynchronous batch submission.
- Registering "just in case" tools without a confirmed gap — over-tooling degrades selection quality more often in production than having too few tools.
- Deploying a write/delete-capable agent tool without a HITL checkpoint because tests never happened to exercise the dangerous path (the agent-file-write Watch Out: validation passing is not the same as the change being safe to commit).
- Assuming a Managed Agents beta session or a consumer surface satisfies HIPAA/GDPR/FedRAMP requirements without checking the specific delivery route's compliance coverage.
- Sending large/repeated images as inline base64 instead of using the Files API, multiplying payload cost on every repeated request.

## Scenario Traps

- Trap: "The output is wrong, so reword the prompt more emphatically." Better: diagnose which of the four techniques (system prompt, XML tags, few-shot, output constraint) is structurally missing and add only that one.
- Trap: "This tool call failed with a validation error about `tool_result`, so the schema must be wrong." Better: check whether the assistant turn came from an interrupted stream first — a mismatched or missing `tool_use_id`, or a partial block from a dropped stream, produces the same symptom.
- Trap: "Extended thinking always improves quality, so enable it everywhere." Better: enable it only for multi-step reasoning or multi-tool planning; for classification/extraction/format tasks it adds cost and carry-back complexity with no accuracy gain.
- Trap: "A tool's input schema is different from another tool's, so Claude won't confuse them." Better: Claude routes primarily on name and description — nearly identical descriptions cause wrong-tool selection even with different schemas.
- Trap: "The stream ended, so the message is complete and safe to save." Better: stream-end and message-complete are different events; only `message_stop` confirms a fully assembled, safe-to-persist turn.
- Trap: "It worked fine through fifty turns in testing, so it will hold in production." Better: production tool outputs are typically 3-5x larger than dev fixtures; measure real-world token cost against your largest expected input before shipping.
- Trap: "This is an agent problem because the tool selections looked wrong after several turns." Better: check whether the context window filled and crowded out the routing instructions before assuming the schema itself is broken.
- Trap: "The task is variable, so it must need a full agent." Better: if the exact steps can still be enumerated in code even with some branching, a workflow with guardrails may be safer and more observable than an agent.
- Trap: "The validation tool passed, so the write is safe to commit." Better: passing a narrow validation check (e.g., a value is within schema range) does not guarantee the change is safe for dependent production systems — irreversible actions need a HITL checkpoint regardless of what validation reports.
- Trap: "In-context memory is simplest, so use it by default." Better: choose memory scope based on session shape (single continuous session vs. many short sessions with accumulated state) at design time, not by default ease-of-implementation.
- Trap: "A subagent inherits everything from its parent, including skills." Better: subagents inherit permission context but not Skills or conversation history automatically — needed Skills must be explicitly configured.
- Trap: "Looping the synchronous API in smaller chunks is basically batching." Better: it is the same number of individual API calls and hits the same rate limits; only the Message Batches API changes the submission model.
- Trap: "The Managed Agents beta is the easiest way to run everything, including regulated workloads." Better: Managed Agents sessions are stateful and server-stored, so they are not eligible for Zero Data Retention or a HIPAA BAA — PHI/ZDR workloads need the Agent SDK or a raw loop on a covered configuration.

## Memorization Cues

- Four prompting techniques, matched to four failure symptoms: wrong shape -> output constraint; drift -> system prompt; hallucinated structure -> few-shot; breaks on a variant -> constraint covering it.
- Structured outputs: JSON outputs constrain the response; strict tool use constrains the tool arguments. Both are enforced at generation time via constrained decoding, not just requested in words.
- Thinking blocks: always round-trip unchanged, signature-verified, redacted blocks included.
- Tool schema anatomy: name, description (when to/when not to use), input_schema (required only when truly required).
- The pairing invariant: every tool_use needs a tool_result with the matching ID in the very next user turn.
- Streaming events in order: message_start -> content_block_start -> content_block_delta -> content_block_stop -> message_delta -> message_stop. Never act before content_block_stop; never persist before message_stop.
- Four context strategies: Pruning (drop what came after a point), Compaction (summarize what stays), Clearing (start over), Subagent Handoffs (isolate and summarize).
- Model tiers, roughly ascending capability/cost: Haiku, Sonnet (default), Opus, Fable (most capable).
- Four memory scopes: In-context (session-only), External storage (cross-session), Summarized (condensed cross-session), Stateless (no persistence).
- Skills load on match; CLAUDE.md loads always (in Claude Code CLI) or per `settingSources` (Agent SDK); in-context instructions grow with the session and vanish with it.
- Image token cost: ceil(width/28) x ceil(height/28) visual tokens.
- Three image-send methods: inline base64 (one-off), URL reference (stable public URL), Files API (reused assets, `file_id`).
- Batches API ceiling: 100,000 requests or 256 MB per batch, whichever comes first; results return unordered — match with `custom_id`.
- HITL question to ask at every irreversible tool: "What is the worst possible outcome if this step runs without a human check?"
