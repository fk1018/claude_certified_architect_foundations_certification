## Key Concepts

| Concept | Study Notes |
|---|---|
| Accelerator | A solution packaged so a future engagement configures a working asset instead of rebuilding from a blank repository. Built by separating customer-specific values from the reusable core and exposing the customer-specific parts as parameters with documented defaults. |
| Three accelerator asset types | Agent Template (system prompt, tool schemas, loop structure -> parameterize domain values), MCP Server Package (tools, inputs, scope -> document each tool input, let the installing team set scope), Eval Suite (dataset + rubric -> ship together so a new team can confirm the asset still works, and reuse the same suite as the deployment gate). |
| Packaging checklist (parameterize / document / bundle for audit) | For every asset type, decide: what to parameterize (values that change per customer: prompts, paths, scopes, credentials by reference, thresholds), what to document (environment assumptions, expected inputs, handled failure modes, the eval that defines "working"), and what to bundle for audit (data touched, identity acted under, log of what the asset did). |
| Hardcoding vs. parameterizing | Hardcoding customer-specific values (repo path, model name, thresholds, prompt fragments) ships faster under deadline but leaves nothing for the next team to configure; they must read the whole file to find load-bearing values, and without documentation or a bundled eval they end up rewriting from scratch. |
| Documentation covers what code cannot show | Code describes behavior; documentation covers the assumptions the asset makes about its environment, the inputs it expects, the failure modes it already handles, and the eval that defines whether it still works. Without it, the next team treats the asset as a black box. |
| Audit log as part of the package | A regulated customer's reviewer asks what data the asset touches, what identity it acts under, and what log it leaves. An accelerator without these passes a demo but stalls at the first security review. |
| Contributing back | Moving an asset from private (internal) reuse to shared infrastructure through a documented channel, so a team that never spoke to you can install it and get the same working setup. An asset already packaged for internal reuse (parameters, documented assumptions, bundled eval) is most of the way to what a maintainer needs. |
| Matching contribution to channel | The Claude Cookbook (GitHub repo of focused, self-contained reference implementations) is for a single- or multi-pattern example demonstrated end to end -- not a full multi-component application. Open-source MCP servers and tools each have their own repository and contribution conventions. A full application sent to the Cookbook stalls because reviewers are set up to review one focused pattern. |
| The four things that make a contribution verifiable | (1) The code does one thing -- a sprawling contribution forces the reviewer to reconstruct intent. (2) An example shows it running -- a reviewer should not have to build a harness. (3) A test proves it works -- lets the maintainer verify without reproducing your reasoning. (4) A short statement names the assumptions -- otherwise the first failure becomes the maintainer's problem. |
| Rights and attribution gate | Licensing and attribution are checked before technical review, because they decide whether a contribution can be accepted at all. Code carried in from a customer engagement may have constraints on where it can go. Confirm the right to contribute it and attribute anything built on. Skipping this turns the contribution into a legal problem later. If a licensing constraint cannot be cleared, escalate to the owner instead of contributing. |
| Functional requirement | Names what the system must do, stated with enough detail to check (e.g., "classify each ticket into one of four queues; draft a reply citing the relevant policy; never auto-send without human approval"). A vague business goal ("help support agents answer faster") is not yet a requirement. |
| Infrastructure requirement | Non-functional constraints the deployment must satisfy, derived by asking questions the business problem implies: Latency (how fast, measured where the user is), Scale (how many requests, at what peak), Residency (where must data be processed, under which regulation), Identity (who acts, under what credentials, what must be auditable). These four most often decide the deployment platform. |
| Documented requirements record | A short record covering functional behaviors, infrastructure constraints, and the regulation each constraint comes from, so a platform choice can be defended as following from requirements rather than from familiarity. Feeds directly into the deployment decision. |
| Systems lifecycle for a Claude application | Requirements (capture functional/infrastructure needs) -> Design (choose platform, model, trust boundaries) -> Build (write agent, tools, prompts) -> Test (evals, unit, integration, end-to-end) -> Deploy (pin version, gate promotion on eval) -> Operate (instrument cost, latency, errors; enforce guardrails) -> Iterate (feed production findings back into requirements). |
| Gates between lifecycle phases | A gate is a decision to move from one phase to the next, and it is where a regulated engagement keeps control: e.g., don't move design -> build until the platform satisfies the residency requirement; don't move deploy -> full production until the new version clears the eval against the pinned baseline. A one-off experiment may collapse phases; a regulated deployment cannot. |
| Deployment platform options | First-party Claude API (Anthropic's own environment, typically gets new features first, no binding cloud/residency constraint). Claude Platform on AWS (accessed via customer's AWS account, Anthropic's own model IDs/lifecycle, but inference is Anthropic-operated outside the AWS boundary). Claude in Amazon Bedrock (Messages API at `/anthropic/v1/messages`, broad feature parity -- confirm feature-specific gaps -- data stays inside the customer's AWS boundary). Claude on Amazon Bedrock (legacy) (InvokeModel/Converse APIs, ARN-versioned model identifiers). Google Vertex AI (Google Cloud identity/IAM, regional or global endpoints). Third-party platforms, e.g., Microsoft Foundry (embeds Claude inside a product the customer already uses; two hosting forms -- Hosted on Azure for a specific model subset with inference end-to-end on Azure, and Hosted on Anthropic for the rest, with inference on Anthropic infrastructure; residency depends on hosting form per model). |
| Customer's existing cloud drives the platform choice | The deployment-platform decision is rarely about technical merit alone; it is usually shaped by where the customer already has cloud infrastructure, identity management, and compliance agreements in place. |
| Identity and data residency are platform-determined | Identity and data location are answered by the platform, not your code. Bedrock uses AWS identity and keeps data inside the customer's AWS boundary; Vertex uses Google Cloud identity and boundary. Both offer regional routing when residency is a constraint. |
| Model alias vs. pinned model ID | An alias (e.g., "claude-haiku-4-5" pre-4.6, or names like "Opus"/"Sonnet") is convenient but evolves over time and may resolve to different versions across platforms -- an upstream change becomes a silent production change. A pinned full model ID (e.g., "claude-haiku-4-5-20251001" pre-4.6) resolves to a fixed snapshot. For Claude 4.6 and later, the model ID alone pins to a specific snapshot; for earlier models, the ID plus a date suffix is required. Always verify the current convention at platform.claude.com at build time. |
| Versioning discipline | Pin the specific model version (not the alias), version the prompt and the asset alongside the code, and keep the prior version available so a regression is a rollback rather than a hotfix. |
| Promotion gated by eval | Send a new model version to a portion of traffic, compare against the pinned baseline using the bundled eval suite, and promote or roll back based on the result. This is the eval acting as the deployment gate, not just a one-time test. |
| Per-platform versioning mechanics | First-party API and Claude Platform on AWS: pin the full model ID (same format), keep the prior snapshot; Anthropic's deprecation schedule applies. Claude in Amazon Bedrock: pin the full model ID with the `anthropic.` prefix; partner retirement dates differ from Anthropic's schedule. Claude on Amazon Bedrock (legacy): pin via ARN-versioned identifiers. Vertex AI: pin the full model ID before rollout using Vertex's format; partner retirement dates differ. Third-party platforms: pin per that platform's own versioning controls. |
| Comparing platforms on latency | Measure from the customer's actual region against their actual payload -- a laptop measurement hides the round-trip penalty. A platform in the customer's region shortens round-trip time; the first-party API is typically advantaged on earliest feature access. Within Bedrock, the global-vs-regional endpoint choice is also the primary residency control and can affect cost. |
| Comparing platforms on compliance | Often the dimension that ends the debate: a customer already certified on one cloud is unlikely to re-certify on another. Data residency = a rule that data must be processed in a specific country/region. The first-party API may not offer EU data residency (verify current coverage); EU-only residency typically requires Bedrock or Vertex AI. On Microsoft Foundry, hosting is per-model: Azure-hosted models run inference end-to-end on Azure, Anthropic-hosted Foundry models do not satisfy EU regional residency. For a regulated customer this is treated as pass/fail, not a tradeoff, and should be raised during scoping, not discovered at contract review. |
| Comparing platforms on cost | Per-token rates are broadly aligned across platforms; total cost moves on egress, platform fees, and integration effort. A lower token price can cost more once transfer and integration are counted. Instrument cost per call for each candidate platform. |
| Multi-component application | Coordinates more than one Claude capability into a single workflow (e.g., an API request triggers a Claude Code task, which reaches a customer system through an MCP server). Each component contributes a capability the others lack; every connection between them creates a place where identity, secrets, and untrusted input can cross. Map which component does what before connecting anything. |
| Trust boundary | The point where data or instructions move from one deployment environment to another -- exactly where injection and access controls apply. Content fetched by a Claude Code task is untrusted the moment it reaches the next component; the receiving component must treat it as data, not instructions. A component being trusted in isolation does not make the seam leaving it trustworthy -- trust does not carry over across a seam; each seam needs its own explicit control. |
| Least privilege across a multi-component app | Each component operates under an identity scoped to only the access its task needs. The application is only as contained as its most privileged seam -- one over-scoped component becomes the weak point even if every other component is properly scoped. |
| Multi-component integration map | First-party API: orchestrates the workflow, holds the entry point; boundary = the request entering from outside; control = input validation + the identity the call runs under. Claude Code task: runs agentic work, may fetch external content; boundary = the fetched content, untrusted downstream; control = treat fetched content as data at the next seam. MCP server: reaches a customer system to read or act; boundary = the system access held on the app's behalf; control = scope to least privilege and log the access. |
| Regulated review requires scoping the whole application | A regulated review requires justifying audit logging, data-residency decisions, and permission controls across the full application, not just one component. For regulated deployments, Bedrock and Vertex AI typically satisfy regional residency constraints. Confirm ZDR (zero data retention) and HIPAA BAA eligibility per component against the Anthropic Trust Center and platform.claude.com before scoping. |
| "Escalate, don't ship around it" pattern | Recurs three times in this module as the fallback when a normal fix isn't available: don't contribute code with an unclearable licensing constraint (escalate to the owner); use full lifecycle gating for a regulated deployment even under deadline pressure; when a trust-boundary seam cannot be secured, escalate to a human owner rather than shipping it. |

## Decision Rules

- If a build will be reused by another engagement, package it while fresh: separate customer-specific values into parameters, document assumptions, and bundle the eval and audit log. If it is a true one-off no one will reuse, skip packaging and ship.
- If a value differs per customer (prompt fragment, path, model name, threshold, scope, credential), it belongs in a parameter with a documented default, not hardcoded in the loop.
- If you are contributing a full multi-component application, do not send it to the Cookbook; strip it to a single focused pattern first, or route the specific piece (tool/server/fix) to its own repository.
- If a contribution lacks a runnable example, a test, or a stated set of assumptions, add them before opening it -- an unverifiable contribution sits at the back of the review queue regardless of code quality.
- If code was carried in from a customer engagement, confirm the right to contribute it and attribute prior work before any technical review; if the licensing constraint can't be cleared, escalate to the owner instead of contributing.
- If a requirement can be checked ("classify into one of four queues"), it is functional; if it constrains where/how fast/under what identity the system runs, it is infrastructure -- capture both before choosing a platform.
- If the customer already holds a compliance certification or cloud relationship, match the platform to it rather than to team familiarity, to avoid a residency review from scratch.
- If a regulated customer has a residency or compliance requirement, treat it as pass/fail and surface it during scoping, before design work is complete -- not at the go/no-go review.
- If shipping to production, pin the full model ID (not a moving alias) and keep the prior pinned version available for rollback.
- If promoting a new model version, gate the promotion on the bundled eval suite against the pinned baseline before sending full traffic to it.
- If measuring latency, compliance, or cost for a platform decision, measure from the customer's actual region/workload/certification -- not from your own laptop or team's default assumptions.
- If two or more Claude-powered components are wired together, mark every seam where data crosses as a trust boundary and add an explicit control there, even if each component passed its own tests in isolation.
- If a Claude Code task or any component fetches external/customer content, treat that content as data at the next seam, never as instructions to the next component.
- If a component needs system access (e.g., an MCP server reaching a customer system), scope its identity to least privilege and log what it does -- the whole app is only as contained as its most privileged seam.
- If a trust-boundary seam cannot be secured with an available control, do not ship around it -- escalate to a human owner.

## Anti-Patterns

- Hardcoding customer-specific values (repo path, model name, thresholds, prompt fragments) into a template and labeling it "reusable" without parameterizing, documenting, or bundling an eval.
- Shipping loose scripts instead of a template -- they run, but each customer-specific value is buried in a different file and diverges across copies instead of being configured in one asset.
- Sending a full multi-component application to the Cookbook instead of a focused, stripped-down example -- reviewers are set up for one pattern, not a whole app.
- Opening a contribution that is "the exact code that solved your problem" with no example, no test, and no stated assumptions -- it works for the author but the maintainer has nothing to verify it with.
- Skipping the rights/attribution check on engagement-derived code and treating licensing as a later cleanup step rather than a gate before technical review.
- Writing only a vague business goal ("be fast and accurate") and treating it as a requirement instead of deriving checkable functional and infrastructure requirements.
- Collapsing lifecycle gates under deadline pressure on a regulated engagement (e.g., moving to build before the platform's residency fit is confirmed, or promoting to full production without clearing the eval gate).
- Deploying against a moving model alias in production because it's the convenient default, with no prior pinned version retained for rollback.
- Choosing a deployment platform on team familiarity/ease of migration without checking the customer's residency or compliance requirements first.
- Measuring latency from a developer's laptop instead of from the customer's actual region and payload.
- Comparing platforms on token price alone while ignoring egress, platform fees, and integration effort, which are what actually move total cost.
- Wiring verified, individually-tested components together and assuming the seam between them is automatically trustworthy.
- Passing content fetched by one component (e.g., a Claude Code task) directly into the next component's call as if it were trusted instructions rather than untrusted data.
- Granting one component in a multi-component app broader access than its task requires, on the assumption that the other components are properly scoped so it "balances out."

## Scenario Traps

- Trap: "The template runs, so it's already an accelerator." Better: a template that runs has not been packaged for reuse -- packaging requires parameters, documented assumptions, and a bundled eval; those are different finishing states.
- Trap: "My PR works for me, so it's ready to submit as-is." Better: a maintainer accepts what they can verify -- add a runnable example, a test, and a short assumptions statement before opening it, or it stalls at the back of the queue.
- Trap: "This is useful, so it belongs in the Cookbook exactly as built, whole application and all." Better: match the contribution to the channel built for its shape; a full application overwhelms a review process built for one focused pattern -- strip it down or route pieces to their own repos.
- Trap: "The platform I know best is the fastest to build on, so it's the right choice." Better: ease of build answers whether the team can ship quickly, not whether the deployment will pass the customer's residency/compliance review -- check compliance constraints during scoping, before committing to a platform.
- Trap: "I measured latency and it looked fine (from my laptop)." Better: latency must be measured from the customer's actual region against their actual payload; a local measurement hides the real round-trip penalty.
- Trap: "Using an alias like 'opus' or 'claude-haiku-4-5' keeps me on the latest model for free." Better: an alias is a moving target that can change output shape without an app-code change; pin the full model ID and keep a prior version to roll back to.
- Trap: "All three components passed their own tests, so the wired-up app is safe." Better: a component trusted in isolation does not make the seam leaving it trustworthy -- every seam where data crosses between components needs its own explicit control.
- Trap: "The MCP server just reaches one customer system, so broad access is fine." Better: least privilege applies per component; the whole app is only as contained as its most privileged seam, so even one over-scoped component undermines the rest.
- Trap: "Compliance and platform choice are things to compare and weigh like latency or cost." Better: for a regulated customer, compliance/residency is typically pass/fail, not a tradeoff to balance against convenience.

## Memorization Cues

- Three accelerator types: Agent Template, MCP Server Package, Eval Suite -- each parameterize / document / bundle-for-audit.
- Contribution readiness = one thing it does + a runnable example + a test + a stated assumption, with rights/attribution cleared first.
- Lifecycle: Requirements -> Design -> Build -> Test -> Deploy -> Operate -> Iterate, with a gate between each phase.
- Requirements split: functional = what it must do (checkable behavior); infrastructure = latency, scale, residency, identity.
- Platform picks itself from the customer's existing cloud/compliance posture, not from team familiarity.
- Alias moves, pinned ID holds still: pin the full model ID, keep the prior version, gate promotion on the eval.
- Compare platforms on three things: latency (measured from the customer's region), compliance (pass/fail for regulated customers), cost (total per call, not token price alone).
- Trust boundary = wherever data crosses between deployment environments; treat fetched content as data, never as instructions.
- An app is only as contained as its most privileged seam -- least privilege must apply to every component, not just the risky-looking one.
- When a seam or a licensing constraint can't be resolved, escalate to a human owner rather than shipping around it.
