## Key Concepts

| Concept | Study Notes |
|---|---|
| Explore, plan, code loop | Claude Code reads and traces the codebase first (explore), proposes a structured plan of edits, then only writes/executes after approval (code). Permission modes plug into this sequence; plan mode holds the agent in the explore phase until you release it. |
| Permission modes | Six modes on a spectrum from most to least gated: default (reads only, prompts on all edits/commands), acceptEdits (auto-approves reads, edits, and common filesystem commands like mkdir/touch/rm/mv/cp/sed inside the working directory; protected paths still prompt), plan (reads only, proposes but never edits), auto (auto-approves everything but a classifier reviews and blocks escalation/unrecognized infra/hostile content; production deploys, mass deletes, credential exfiltration, and force-push to main stay blocked), dontAsk (only pre-approved allow-listed tools plus read-only commands run; everything else auto-denies, no queue), bypassPermissions (all tool calls run with no prompts and no safety checks except catastrophic rm -rf / or rm -rf ~; also skips the protected-path guard the other modes keep). |
| Settings hierarchy and scope | User level (~/.claude/settings.json) applies machine-wide. Project level (.claude/settings.json, committed) applies to everyone who clones the repo. Local project level (.claude/settings.local.json) is personal and git-ignored. Enterprise level (managed-settings.json, admin-controlled) cannot be overridden by users or project files and is the most durable governance control. |
| Allow/deny rule precedence | A deny rule always wins over an allow rule regardless of mode. An enterprise-level deny rule cannot be removed by any individual developer and applies even under a bypass mode. |
| Placing the human gate | The gate placement question is the same one that separates safe from risky permission modes: what is the worst outcome if this action runs unchecked? Low-stakes/reversible actions (formatting, working-directory edits) can pass without a gate. Hard-to-undo or sensitive-path actions (writes outside the working directory, destructive shell commands, edits to protected files) need a gate: a deny rule enforces this deterministically, default/plan mode keeps a prompt in place. Sensitive code changes should never have the agent as the only reviewer — a human must review before merge regardless of confidence. |
| bypassPermissions risk | Bypass mode removes every checkpoint, including the protected-path guard the other modes keep. A broad file-match pattern (e.g. a cleanup script matching more paths than intended) can delete production config with no prompt to catch it. Only appropriate inside an isolated, disposable container/VM, never on a developer workstation against live files. |
| CLAUDE.md | A file at the project root that Claude Code reads at the start of every session; its contents are appended to the prompt before any user message. Generated by /init as a starting point, but must be validated. Holds universal constraints: testing commands, framework conventions, off-limits paths, style decisions. |
| CLAUDE.md dilution | Every line added reduces the effective weight of every other line, since more content consumes more of the context window. A CLAUDE.md that grows into a historical log (e.g. 800+ lines) can bury a critical path restriction so deeply that the agent violates it despite the rule being present. Move historical/reference content out; keep only session-critical rules. The rule that must never be diluted is the one that should become a hook instead. |
| Rules instruction files | Live in .claude/rules/, scoped to specific paths via a `paths` glob in YAML frontmatter. A scoped rule only enters context when Claude works with matching files, avoiding clutter elsewhere. A rules file WITHOUT a `paths` field loads unconditionally at session start, with the same priority as CLAUDE.md — scoping comes from frontmatter, not from directory placement (subdirectories under .claude/rules/ are organizational only). |
| Hooks | Intercept and control tool calls at fixed lifecycle points, defined in settings files and configured via /hooks. Unlike a CLAUDE.md instruction (which the model usually but not always follows), a hook fires deterministically every time, independent of model decisions. Core events: PreToolUse (runs before a tool call; can exit code 2 to block it, writing the reason to stderr — the only event that can block), PostToolUse (runs after; cannot block, good for formatting/tests/audit logging), UserPromptSubmit (runs on prompt submission, before model processing; inject context or validate), Stop (runs when the model finishes responding; notifications/cleanup/audit commit), Notification (fires on permission requests or after 60s idle; route to external channel), SessionStart (init state, validate env vars/services), SessionEnd (teardown, final audit writes). |
| Subagents | Specialized assistants that run a delegated task in an isolated context; they do not inherit main conversation history, accumulated files, or session state, and return only their output. Built-in Explore and Plan subagents skip CLAUDE.md and git status to stay fast/cheap — project rules do NOT apply to them. The general-purpose subagent loads both. Custom subagents (.claude/agents) do not automatically see skills; a skill must be explicitly listed in the subagent's frontmatter. |
| Skills across runtimes | A SKILL.md file in .claude/skills, portable in principle across Claude Code, Messages API, Agent SDK, and Claude Managed Agents — but each runtime loads/sandboxes it differently. Claude Code: discovered from filesystem, runs locally under permission mode/deny rules. Messages API: sent with the request, runs inside Anthropic's code-execution container (not local files), requires code-execution and skills beta headers. Agent SDK: loading of filesystem settings (CLAUDE.md, skills) is controlled by settingSources (TS)/setting_sources (Python) — must be set explicitly, never assume a default. Claude Managed Agents: skills attached when defining the agent as an API resource (managed-agents-2026-04-01 beta header); runs in an Anthropic-provisioned sandbox with no filesystem discovery; not eligible for Zero Data Retention or HIPAA BAA currently. |
| Skill portability rules | (1) Write the description as the matching criterion — vague descriptions fail to load in every runtime. (2) Don't assume a local filesystem or local tools exist in the skill body — a skill that shells out locally breaks on the Messages API container. (3) Subagents don't inherit skills automatically in any runtime — list them explicitly. |
| Custom commands vs. skills | Skills are the current recommended format for both explicit (/skill-name) and automatic (description-match) invocation. The older .claude/commands/ directory format still works but is legacy. Use `disable-model-invocation: true` in a skill's frontmatter for a workflow that should only run when explicitly called. |
| Plugins | Bundle skills, hooks, subagents, and MCP servers into a single installable unit, distributed through a marketplace (a catalog of shared plugins). Plugin commands are namespaced by plugin name (a run-tests command in plugin "payments" becomes /payments:run-tests), so renaming a plugin renames all its commands. |
| Plugin path portability | A plugin that hard-codes an absolute path (e.g. /Users/alexmorgan/...) installs correctly everywhere but only executes correctly on the author's machine. Use $CLAUDE_PROJECT_DIR for scripts in the project and ${CLAUDE_PLUGIN_ROOT} for scripts bundled inside the plugin. Any required environment variable must be documented and validated at install time, or the failure surfaces silently mid-run on a teammate's machine. Test install on a clean machine before distributing. Deny rules/hooks relied on locally are NOT automatically included in a plugin bundle — only what's explicitly packaged travels with it. |
| Marketplace and enterprise plugin deployment | The official Anthropic marketplace is available by default; third-party marketplaces are added via `/plugin marketplace add <owner/repo>` (hosted in a GitHub repo). Enterprise admins can deploy plugins org-wide through managed settings: a managed marketplace allowlist gates which sources users may add (but doesn't auto-register them), and pairing it with `extraKnownMarketplaces` pushes a marketplace to all users without requiring them to add it manually. Managed-scope deployment sits above user and project settings and cannot be overridden. |
| MCP server fundamentals | An MCP server is a standalone process exposing tools, resources, and prompts that any MCP client can use — build the capability once, every client benefits, instead of each application re-implementing its own integration. Claude Code has a built-in MCP client that discovers and invokes a connected server's tools. |
| MCP resources and prompts | A resource is read-only data placed directly into context (not fetched via a tool call) — a direct resource has a fixed address (e.g. a document list), a templated resource takes a parameter (e.g. a document ID). Use a resource when data should be in context predictably from turn start. A prompt is a pre-written instruction template a client can invoke by name instead of the user writing their own wording — useful when carefully engineered wording produces materially better results and should be consistent across every client. Resource support varies by MCP client — verify before relying on it. |
| MCP transport | stdio: local subprocess, client launches server and talks over stdin/stdout — correct for a personal/local/dev server, cannot be shared or hosted remotely. HTTP: the recommended transport for any non-local server — you register a URL and the client connects over the network; used for shared team servers and hosted integrations. SSE: legacy, superseded by HTTP transport, not recommended for new servers. |
| MCP context cost and tool discovery | By default Claude Code defers loading connected servers' tool definitions and uses an agentic search step to discover/load only what a task needs, rather than loading every definition up front. An opt-in mode loads definitions upfront when they fit within roughly 10% of the context window, deferring only past that. Connecting only the servers a task needs keeps requests lean. |
| Prompt caching | Caches the processing work on a stable prefix of a request so a follow-up reusing that prefix pays a fraction of the cost instead of reprocessing from scratch. Marked with a `cache_control` field of type `ephemeral` on the last block to cache (caches everything up to and including it); up to 4 breakpoints allowed. Requests process in fixed order (tools, system prompt, messages), so a breakpoint after tools caches tool definitions while keeping messages dynamic. Default cache lifetime is 5 minutes from last read (resets on each read); an opt-in 1-hour TTL suits workloads with longer gaps between requests. A single changed character before the cache point invalidates the cache. Caching only applies above a minimum token threshold (1,024 tokens for most current models). |
| RAG: classical vs. agentic search | Both retrieve a relevant slice of material instead of loading everything into context; the difference is timing. Classical RAG pre-indexes: chunks are embedded and stored in a vector database in advance, then a query embedding is matched against it at request time. Agentic search has no pre-built index — the model figures out what it needs at the moment of the request and fetches it live (e.g. Claude Code's on-demand MCP tool discovery, or Claude.ai Projects surfacing only relevant document sections). Retrieval scales (cost per request stays roughly flat as source material grows) but is only as good as what it finds — descriptive file/document naming and organization materially improve retrieval quality. |
| MCP configuration scope | Local scope: stored in ~/.claude.json under the current project path, personal and not shared. User scope: personal Claude settings, available across all your projects but still not shared with teammates or written to the repo. Project scope: written to .mcp.json at repo root; committing it gives every clone the same server automatically — for a stdio server this means every teammate spawns their own local subprocess and needs the runtime (e.g. Node) installed locally. Enterprise scope: centrally managed by an administrator, pushed to all org users without individual configuration. |
| Per-tool MCP permission rules | Permission rules can target one tool on a server using the form `mcp__server__tool` rather than gating the whole server. An allow rule on `mcp__github__create_issue` lets only that tool run without a prompt while other GitHub tools still prompt; a deny rule on a write-capable tool blocks it while read-only tools on the same server remain available. A deny on one tool overrides an allow on the whole server. The API's MCP connector separately offers an `mcp_toolset` object with a per-tool `enabled` flag — this is a context-cost/scope control (whether the model even sees the tool), distinct from a permission rule (whether an exposed tool may run). |
| GitHub MCP server (worked example) | Remote, HTTP transport (hosted by GitHub) — register by URL. Authenticates via a Personal Access Token passed as a Bearer token in the request header, supplied through an environment variable and referenced (never inlined) in the MCP config, because an inline token written to a committed file enters repo history irrecoverably. Choose project scope for whole-team repo tooling, local scope for personal-only access. |
| Linear MCP server (worked example, contrast) | Remote, HTTP transport, but authenticates via OAuth instead of a static token: the server returns 401 Unauthorized, the client opens a browser-based sign-in flow, and after approval a token is issued and stored automatically — no manual secret copying. OAuth is the right pattern whenever the service's authorization model is tied to individual user identity. |
| Authentication pattern by service type | Remote service with user identity (SaaS/cloud) → OAuth. Remote service with service identity (internal API) → API key in an environment variable, never committed. Local service with filesystem access → stdio transport with no network auth; the filesystem permission model (deny rules) is the governance layer. |
| Credential leakage failure mode | An API key placed inline in .mcp.json "temporarily" and then committed spreads immediately (local machine, repo history, every clone, CI runner) — moving it to an env var afterward and re-committing does NOT remove it from history; the credential must be treated as compromised and rotated, which can break other services configured with the same key. |
| Three secret-handling practices | (1) Separation: the config file holds only a variable reference, never the value — configs get committed/shared/cloned and an inline value travels with every copy. (2) Storage location: an environment variable is enough for a value local to one machine/pipeline run; a secret store (a managed service that returns credentials to authorized callers at runtime and records who read what) is better for values shared across services/people, since one rotation updates every consumer. (3) Rotation: replace a credential on a schedule and immediately after any suspected exposure — rotation is the only valid response to a leak, and inline-committed values cannot be cleanly rotated because history retains the old value and hardcoded consumers break. Scope each credential to the narrowest access needed. |
| Defending against inline credential writes | Two layers: a CLAUDE.md convention instruction stating credential values must never be written inline to .mcp.json (signals intent to the model each session), backed by a PreToolUse hook that inspects write/edit operations against .mcp.json for credential-shaped patterns and blocks (exit code 2) if found. The instruction communicates intent; the hook enforces it deterministically — same hook-vs-instruction distinction as the CLAUDE.md dilution scenario. |
| Enterprise integration questions | Beyond "does the connection work?": Who is the model acting as, and is that identity auditable? What data can it access and where does it leave the organization? Can an admin lock the configuration so no developer can change auth setup? Can access be logged to satisfy a compliance audit? |
| OAuth redirect URI per-environment trap | OAuth redirect URIs are registered per host. A connection working end-to-end in staging does not mean production is authorized — the production host must be separately added to the OAuth app's allowed redirect URI list, or every sign-in attempt fails with a redirect URI mismatch and loops back to the sign-in screen. Many regulated customers additionally require separate OAuth app registrations per environment (not just per-host URIs on one app), as a security policy matter. Include registration as an explicit deployment-checklist step. |
| Audit logging and data residency | A PostToolUse hook that logs every tool call and its parameters to an audit store answers the compliance logging question deterministically (fires regardless of model behavior). Data residency is answered by pairing an HTTP endpoint pinned to a specific region with a platform deployment that pins processing to that region — a checkable answer for a compliance reviewer. |
| Code modernization as a module-wide test case | High-blast-radius legacy work concentrates every risk this module addresses. Use the explore/plan/code loop with plan mode to review proposed edits before any file changes; hooks to block edits to sensitive paths during risky phases; CLAUDE.md to carry new target-pattern conventions so the agent doesn't drift back to legacy patterns it reads nearby. Before starting, answer three scoping questions: What is the blast radius if something goes wrong? How are changes audited (is there a PostToolUse hook and does its log satisfy the reviewer)? Who approves each phase before the next begins? |
| AI code review trust calibration | Trust findings the reviewer can prove directly from the diff in front of it (e.g. a missing null check, an unclosed resource) and verify them on the cited lines. Treat any claim about runtime behavior or another system as an unproven hypothesis to test, since the reviewer lacks the evidence to prove such a claim. Place the human gate at the point where a finding becomes a hard-to-reverse action. |

## Decision Rules

- If the work is unfamiliar-codebase or high-stakes, default to `default` or `plan` mode; only move to `acceptEdits` for trusted local work, and only ever consider `bypassPermissions` inside a disposable, isolated container.
- If an action is hard to undo, touches a path outside the working directory, or reaches a security-relevant/protected file, put a human gate there regardless of the permission mode in effect — a deny rule enforces this deterministically.
- If a change touches code the team has marked sensitive, never let the agent's own review stand in for human review before merge, no matter how confident it sounds.
- If a rule must apply everywhere in the project and rarely changes, put it in CLAUDE.md; if it only matters for a subset of files, scope it in a rules file with a `paths` glob instead of bloating CLAUDE.md.
- If a behavior must happen every single time with no exceptions (formatting, blocking a path, audit logging), use a hook — a CLAUDE.md instruction is followed most of the time, not deterministically.
- If a task is exploration/investigation that would bloat the main context, or needs to run in parallel, delegate to a subagent — but if project rules (CLAUDE.md) must apply to that work, use the general-purpose or a custom subagent, not the built-in Explore/Plan subagents.
- If a workflow needs to run identically across Claude Code, the Messages API, and the Agent SDK, write it as a skill with a description written as the matching criterion, and avoid any assumption of a local filesystem or local tools in its body.
- If a setup currently lives on one developer's machine and needs to be shared/versioned across a team, package it as a plugin rather than asking everyone to replicate manual steps — but reference paths via `$CLAUDE_PROJECT_DIR` or `${CLAUDE_PLUGIN_ROOT}`, never an absolute path.
- If a server runs only on your own machine, use stdio transport and local (or user) scope; if a server is hosted remotely and shared by a team, use HTTP transport and project or enterprise scope. A stdio server cannot be meaningfully project-scoped for team sharing.
- If a service authenticates by individual user identity, use OAuth; if it authenticates as a service account, use an API key delivered through an environment variable, never committed inline.
- If moving an OAuth-authenticated MCP integration to a new environment (e.g. staging to production), register that host's redirect URI (and consider a separate OAuth app registration) before assuming the connection will work.
- If a regulated customer will review the integration, plan for admin-lockable configuration (enterprise managed settings), audit logging (PostToolUse hooks), and documented data residency before the deployment, not after a failed review.

## Anti-Patterns

- Switching to `bypassPermissions` "because the work feels routine" — it also silently removes the protected-path guard that every other mode keeps.
- Letting CLAUDE.md grow into a historical decision log or archive; every added line dilutes the weight of every other rule, including the one that matters most.
- Treating an unscoped rules file as automatically narrow because it lives in a subdirectory of .claude/rules/ — scoping comes only from the `paths` frontmatter field.
- Relying on a CLAUDE.md instruction alone to enforce something that must never fail (e.g. a path restriction, a credential-inline ban) instead of backing it with a PreToolUse hook.
- Assuming a subagent inherits your project rules or skills by default — Explore/Plan skip CLAUDE.md, and no subagent auto-loads skills.
- Writing a skill or plugin component with an absolute path or an undocumented required environment variable, then distributing it — it installs everywhere and runs nowhere but the author's machine.
- Committing an MCP server's API key inline in .mcp.json "temporarily" — a later commit that removes it does not remove it from git history; the key must be treated as compromised.
- Assuming a stdio server can be shared like an HTTP server by committing it to .mcp.json — it still spawns a local subprocess per machine and requires the runtime installed locally on each teammate's system.
- Assuming a staging OAuth connection proves production is configured — redirect URIs are registered per host, and regulated customers often require separate app registrations per environment.
- Treating an AI code reviewer's claim about runtime or cross-system behavior as verified fact just because the finding sounds confident and specific.

## Scenario Traps

- Trap: "acceptEdits is basically as safe as default since it still gates non-filesystem shell commands." Better: acceptEdits auto-approves common filesystem commands including `rm` inside the working directory — only `default` mode prompts before those.
- Trap: "The plugin installed successfully on every teammate's machine, so it will run successfully too." Better: installation only means files were copied into place; execution resolves paths and environment variables against the machine actually running it, which is where author-specific absolute paths and undocumented env vars fail silently.
- Trap: "I moved the leaked API key to an environment variable and committed the fix, so the exposure is resolved." Better: the old value remains in git history forever; only rotation removes the exposure.
- Trap: "The OAuth flow passed every staging test, so production will just work when we deploy." Better: OAuth redirect URIs are registered per host — the production host must be separately authorized, and some enterprise policies require a wholly separate app registration per environment.
- Trap: "A rules file inside .claude/rules/database/ is automatically scoped to the database code." Better: scoping only happens through the `paths` glob in the file's frontmatter; without it, the rule loads unconditionally like CLAUDE.md regardless of which subdirectory it sits in.
- Trap: "Explore and Plan subagents will respect the constraints in my CLAUDE.md since it's a subagent within the same project." Better: the built-in Explore and Plan subagents skip CLAUDE.md and git status by design to stay fast — use general-purpose or a custom subagent when project rules must be honored.
- Trap: "A deny rule on Bash(rm:*) is redundant once I also set defaultMode to default." Better: deny rules provide deterministic, mode-independent protection — they still apply even under a bypass mode, whereas mode alone can be changed mid-session.
- Trap: "The AI code reviewer said this function has a race condition under concurrent load, so I'll fix it." Better: a claim about runtime/concurrency behavior is a hypothesis the reviewer cannot prove from the diff alone — treat it as something to test, not a verdict to apply directly.

## Memorization Cues

- Six permission modes, ascending trust: default → acceptEdits → auto → dontAsk → bypassPermissions, with plan as a parallel read-only branch that gates ALL edits until approval.
- Deny beats allow, always, everywhere — even under bypassPermissions for enterprise-level deny rules.
- Four settings scopes: User (~/.claude), Project (.claude, committed), Local (.claude, gitignored), Enterprise (managed-settings.json, un-overridable).
- CLAUDE.md = always on, dilutes with size. Rules file = scoped by frontmatter `paths`, not folder. Hook = deterministic, fires regardless of model decision. Subagent = isolated context, returns only output.
- PreToolUse can block (exit code 2); PostToolUse cannot block but is right for side effects/audit logging.
- Skill portability = clear description + no local-environment assumptions + explicit subagent skill listing.
- Plugin path safety = `$CLAUDE_PROJECT_DIR` (project scripts) and `${CLAUDE_PLUGIN_ROOT}` (bundled plugin scripts), never an absolute path.
- Transport follows location: stdio = same machine, HTTP = remote/shared, SSE = legacy, avoid.
- Scope follows sharing intent: Local = just me, this project; User = just me, every project; Project (.mcp.json) = whole team via repo; Enterprise = whole org via admin.
- Auth follows identity model: user identity → OAuth; service identity → API key via env var; local filesystem → no network auth, deny rules are the boundary.
- Secrets: never inline, always referenced by variable; overwriting a committed secret does not erase history — only rotation does.
- OAuth redirect URIs are per-host; staging success says nothing about production authorization.
- Cache breakpoints: up to 4, `cache_control: ephemeral`, 5-minute default TTL (resets on read) or opt-in 1-hour TTL, 1,024-token minimum.
