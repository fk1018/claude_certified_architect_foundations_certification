## Key Concepts

| Concept | Study Notes |
|---|---|
| Design document | A short markdown file written before production code that states four decisions: success criteria (specific enough to grade), failure handling (retriable/terminal per error, and what the user sees), cost/latency budget (ceiling plus reliability floor), and trust boundary (untrusted inputs, minimum access). Each later layer in the module derives directly from one of these four decisions. |
| Eval pipeline | `run_test_case` runs one case and grades it; `run_eval` loops over a dataset and averages scores. Write the eval before the feature — it forces success criteria to be defined up front rather than rationalized after the fact. The absolute score matters less than whether it moves when you change one lever at a time. |
| Grading method selection | Exact/string match: one correct form, cheapest, brittle against paraphrase. Code-graded check: validates structure (parseable JSON/Python, required fields, ranges) without judging content quality. LLM-as-judge: only method that scores open-ended quality (faithfulness, instruction-following); most expensive and noisiest, and must be calibrated. |
| Judge calibration | Ask the judge for strengths/weaknesses/reasoning alongside the score, not the score alone — otherwise judges drift to a "safe" middle number (around 6) regardless of quality. Calibrate by running the judge against a human-labeled set and measuring agreement; if agreement is low, tighten the rubric with good/bad examples and re-measure. |
| Coverage over perfection | A larger eval set with slightly noisier automated grading typically catches more regressions than a small, perfectly hand-graded set. Use Claude to generate additional edge cases from a small labeled seed set, then spot-check them. |
| One-lever-at-a-time iteration | Change only the prompt, the tools, or the model between eval runs — never more than one at once — so you know which change caused a score movement. Read per-case results, not just the average, since a steady average can hide cases that improved masking cases that regressed. |
| Four test levels | Unit (one function in isolation), functional (one Claude call returns the expected shape), integration (the handoff between two components — where most silent production failures hide), end-to-end (the full flow as a user runs it — slowest, hardest to localize but catches whole-flow breaks). |
| Tracing | A recorded timeline of each step in a run (prompt, tool calls, intermediate outputs, timing) that localizes a failure to a specific step, turning a vague "the eval score dropped" into "step 4, the parser, raised a KeyError." |
| Retrieval routing | A cheap classifier call routes single-fact lookups to a fetch-once static retrieval path and multi-part questions to an iterative agentic-search path, so you pay for iteration only when the query needs it. |
| Retriable vs. terminal errors | The test: would retrying the identical request plausibly succeed? Retriable = transient (429 rate limit, 529 overloaded, 500/502/503/504 server errors) — handle with backoff. Terminal = the request itself is wrong (400 bad request, 401 auth, 403 forbidden, 404 not found) — retrying wastes budget and hides the real problem. When unsure, default to terminal (fails loudly, gets fixed) rather than retriable (hammers the service silently). |
| SDK built-in retries | Anthropic client libraries already retry transient failures with progressive delay up to a configurable attempt count. Adding your own retry loop on top double-retries the same failure against the same limit — decide explicitly whether the SDK or your own code owns retries, not both. |
| `retry-after` header | A 429/529 response can include `retry-after`, telling you precisely how long to wait. Treat it as authoritative when present; fall back to exponential backoff only when it is absent. |
| Tool error surfacing | A failed tool call must be returned to Claude as a `tool_result` with `is_error: true` and a message — never as a silent empty result. An empty result is read by the model as valid data, producing a confident wrong answer built on nothing. |
| Refusal handling | A model refusal arrives as a 200 HTTP status with `stop_reason: "refusal"` — the standard retriable/terminal status-code classifier will not catch it. Treat it as fail-fast: raise, log, and require input review; do not silently retry or accept it as valid output. |
| Model tiers | Fable: most capable, for the most demanding reasoning/coding/agentic work. Opus: demanding work above the Sonnet envelope. Sonnet: balanced default for most production workloads. Haiku: speed and cost efficiency for tasks that fit its envelope. Default to Sonnet; move up only when an eval shows Sonnet missing the quality bar; move down only when an eval shows the cheaper model still holds the bar. |
| Model routing | A default model plus an override triggered by a cheap signal (task type, input length, difficulty classification) sends the bulk of traffic to a balanced model and routes only the requests that need it to a larger (or smaller) tier — mirrors the retrieval-routing pattern applied to model choice. |
| Per-call observability | Instrument three metrics on every call: token usage (input/output), latency, and error rate. Per-call logging turns "why is the bill high" into "which step, on which request type" — a flow that looks uniformly expensive often has one step doing ~90% of spend. |
| Streaming with tool use | In a streaming response, `tool_use` blocks arrive as a sequence of `content_block_start`/`content_block_delta` (`input_json_delta`) events and must be accumulated by index until the stream closes before the JSON input is complete and safe to act on. Acting on a partial block produces malformed tool inputs; a broken stream mid-response should be retried as a transient failure, not passed downstream partially. |
| Prompt caching mechanics | Caches the token-processing work for a stable prefix so a repeat request reads it back instead of reprocessing. Cache writes cost a premium over base input tokens (1.25x for 5-minute TTL, 2x for 1-hour TTL); cache reads cost a fraction of standard input (0.1x) — so caching only pays off when reads outnumber writes. Requires an exact-match prefix (any change before the breakpoint, even one word, invalidates the cache) and a minimum prefix length that varies by model. Best on long, stable system prompts and tool schemas; a stale cache is a real trade-off if the cached content needs to reflect changing data. |
| Message Batches API | Processes requests asynchronously at a lower per-request cost, trading immediate latency for a cheaper bill. Right for non-urgent, high-volume, schedule-driven work (overnight jobs, backfills, reports); wrong for anything a user is waiting on. Batching and prompt caching compound when a scheduled job reuses the same long system prompt across many batched requests. |
| Orchestrator-worker pattern | A lead agent decomposes a task, delegates subtasks to parallel subagents each with its own context window, then synthesizes their results. Anthropic reported this pattern using roughly 15x the tokens of a single-agent chat interaction, and reported it improving on tightly-coupled tasks like coding much less than on independently-splittable tasks like multi-source research, because token usage accounted for most of the reported performance variance. Use it only when the task genuinely decomposes into independent parallel parts; use a more capable model as lead and cheaper models as workers to control the multiplier. Failure handling must be replicated independently per subagent — the pattern multiplies failure surface, not just cost. |
| Reliability floor | Define a minimum retry budget and latency ceiling first, then optimize cost above that floor, never below it. Cost pressure is louder (visible on a dashboard daily) than reliability pressure (occasional failures dismissed as noise), so setting the floor first prevents cost optimization from silently eating reliability. The pinned eval baseline score is what makes the floor checkable/enforceable as a gate. |
| Prompt injection | The model reads its whole context as one undifferentiated stream of tokens with no structural marker separating trusted instructions from untrusted retrieved content. An instruction hidden in a fetched page, document, tool result, or any content someone else can write is read exactly like a user command. Injection can be indirect (planted for later reading) and hidden (white text, off-screen, inside an image). Trusting your own users does not help, because the hostile instruction arrives through content the agent reads, not through the user's own prompt. |
| Prompt injection defense | Two-sided: (1) treat all fetched/retrieved content as data to be examined, never as instructions — delimiters help but are a soft boundary since untrusted content can mimic them; model training and classifiers raise the bar but are probabilistic, not guaranteed; (2) constrain and log what the agent is allowed to *do* regardless of what the content says — the reliable boundary lives in enforced action limits, not in prompt wording. |
| Jailbreak vs. prompt injection | A jailbreak targets the model's own safety training (get it to ignore its constraints); a prompt injection targets the application's instructions (hijack what the agent does on the app's behalf). Different targets, same layered defense shape: validate/constrain what reaches the model, and limit what the model is allowed to do as a result. |
| Least privilege | A production agent's identity should carry only the narrowest permissions the task requires (explicit allow-write/allow-read/deny lists). It is the control that holds even when every other layer fails — if a steered agent's identity can only write to one output directory, a successful injection becomes a denied action and a log entry rather than an incident. Anything that can modify the agent's own auth/role configuration can effectively act with that widened identity, so protecting that configuration matters as much as protecting secrets. |
| Secret management | Secrets belong in environment variables or a secret manager, never in committed configuration — a secret in repo history is a permanent exposure even after later removal, and rotation (the correct response to a leak) is impossible for something baked into source. |
| Hook-based guardrails | A `PreToolUse` hook runs before a tool executes and can return `permissionDecision: "deny"` or `"allow"`, with reasoning, blocking a call before it runs and logging both blocked and permitted privileged actions. A rule that lives only in a prompt is not enforced; a hook that runs before execution is. When multiple rules/hooks apply, precedence is deny over ask over allow — one deny blocks the action regardless of how many allows also match. |
| Regulated-review scoping | A financial/healthcare customer asks three questions early: where is data processed (data residency), how is access logged (maps to hook audit logging), and can configuration be centrally managed (prevents an individual developer from quietly widening permissions). Naming these during scoping, before the review, keeps the integration from stalling. |
| ZDR eligibility | Zero Data Retention eligibility varies by model and by platform and is not guaranteed even under an existing ZDR agreement; not all current models are ZDR-eligible, and newer/higher-capability models may not have confirmed ZDR status. Confirm current eligibility against the Anthropic Trust Center at scoping time, and confirm retention separately per cloud platform (Bedrock, Vertex AI, Foundry) if deploying there. |
| OS-level sandboxing | The residual control below hooks and least-privilege roles: filesystem isolation restricts the agent to its working directory and network isolation restricts outbound connections to named endpoints, enforced by the operating system rather than application logic. It closes the gap a hook or permission rule can miss by not explicitly covering a path or endpoint, and it holds even when a hook is missing, misconfigured, or bypassed. Configured via Claude Code settings; documented at code.claude.com. |
| Layered security | No single control is sufficient alone: model training/classifiers reduce how often an injection lands, treating content as data reduces how often a landed injection is acted on, least privilege and locked config bound what a successful action can reach, hooks enforce and record those boundaries, sandboxing closes gaps hooks don't cover, and regulated-review scoping makes the whole arrangement explainable to a reviewer. A defense depending on one control failing closed collapses on that one bug; a layered defense degrades instead. |

## Decision Rules

- If you are about to ship a feature and "done" is based on watching it work a handful of times by hand, write a graded eval set first — a handful of manual tries only covers the input shapes you happened to picture.
- If the output has exactly one correct form, use exact/string match. If the output must satisfy a structural rule (valid JSON, required fields, a numeric range) but content can vary, use a code-graded check. If quality is open-ended (faithfulness, tone, completeness), use an LLM-as-judge, and calibrate it against human-labeled cases before trusting its scores.
- If an eval or test fails, read the trace before touching code — localize the failing step first, then apply the fix at that step, not somewhere it merely feels wrong.
- If two components each pass their own tests but the full flow fails, suspect the handoff between them (a format contract mismatch) and add an integration test that drives both together with real data — a unit or functional test cannot catch a seam failure.
- If an error's cause is transient (rate limit, overload, timeout, a 5xx server fault), treat it as retriable and back off with a cap, honoring `retry-after` when present. If the cause is in the request itself (bad input, auth, permissions, missing resource), treat it as terminal and fail fast — never retry it.
- If you are uncertain whether an error is retriable, default to terminal — a wrongly-terminal error fails loudly and gets fixed, while a wrongly-retriable error hammers the service silently.
- If a tool call fails, return the error to Claude with `is_error: true` — never return an empty or silent result, or the model will reason on top of missing data as if it were real.
- If a model response arrives as HTTP 200 with `stop_reason: "refusal"`, treat it as fail-fast and do not run it through the retriable-error classifier — it will not be caught there.
- If you are choosing a model tier, start with Sonnet, and change tier only on eval evidence — step up when Sonnet misses the quality bar on hard cases (especially where a wrong answer is costly), step down when a cheaper tier still holds the bar.
- If traffic is mixed (some simple, some complex), route with a default model plus an override on a cheap difficulty signal rather than pinning one tier for everything or running every request through the most capable model.
- If a system will run at volume, instrument token usage, latency, and error rate on every call from day one — don't wait for an invoice to tell you where the spend is.
- If content is stable and reused across many requests (a long system prompt, a fixed tool schema), enable prompt caching; if the same content is needed only rarely within the cache TTL, or if it must reflect frequently-changing state, caching adds cost/staleness risk without benefit.
- If work is non-urgent, high-volume, and schedule-driven, use the Message Batches API for the cost discount; if a user is waiting on the response, batching is the wrong tool and streaming is the latency lever instead.
- If a task genuinely decomposes into independent parts that can be explored in parallel (e.g., research across separate sources), consider an orchestrator-worker pattern; if the task is tightly coupled with each step depending on the last (e.g., most coding tasks), use a single agent — fan-out there only multiplies cost without adding value.
- If you use an orchestrator-worker pattern, replicate the same retry/backoff/fallback discipline independently in every subagent — a single stalled subagent with no backoff can block the whole synthesis step.
- If you are setting a cost budget, set the reliability floor (retry budget, latency ceiling, minimum eval score) first, then optimize cost above it — never optimize cost first and discover the floor only after crossing it.
- If an agent reads any content it did not author (a fetched page, a document, a tool result, an email body, a database record), treat that content as data to examine, never as instructions to follow, regardless of how trusted the user who triggered the read is.
- If a rule about agent behavior must actually hold under adversarial input, enforce it with a `PreToolUse` hook that can deny the action before it executes — a prompt-only instruction is not a security control.
- If you are scoping a production agent's identity, grant the narrowest permissions the task needs (explicit allow-lists plus explicit denies) and protect the auth/role configuration itself as a privileged resource, since anything that can widen it can act with the widened identity.
- If you are scoping for a regulated customer, name data residency, access logging, and managed/central configuration up front, and confirm each candidate model's current ZDR eligibility (and platform-specific retention) before committing to a deployment surface.
- If a hook, deny-list, or role scope might not cover every path or endpoint an agent could reach, add OS-level filesystem and network sandboxing as the control that holds even when a specific rule is missing or misconfigured.

## Anti-Patterns

- Judging a feature "done" from a dozen manual tries instead of a graded eval set — the manual tries only cover the input shapes the builder happened to imagine (the two-dates extraction failure).
- Using an LLM-as-judge score without calibrating it against human-labeled cases first — an uncalibrated judge produces a confident-looking number that means nothing.
- Changing the prompt, the tools, and the model all in the same eval iteration — if the score moves, you cannot tell which change caused it.
- Trusting that two components are correct together because each passes its own unit or functional test — the handoff between them is exactly where silent failures hide, and only an integration test exercises it.
- Shipping without an error path because development traffic never triggered a rate limit, timeout, or transient failure — the first production traffic peak becomes the first time the missing path is discovered.
- Retrying a terminal error (bad request, auth failure) — it wastes the retry budget and produces an identical failure every time, hiding the real problem behind a wall of retries.
- Writing an immediate, uncapped retry loop for a rate-limit error — hammering the same limit deepens it instead of relieving it; always back off with a cap and honor `retry-after`.
- Running your own retry loop on top of the SDK's built-in retries without disabling one of them — this multiplies attempts against the same limit rather than capping them.
- Letting a failed tool call return a silent empty result instead of `is_error: true` — the model treats the empty result as valid data and produces a confident wrong answer.
- Reaching for the most capable model tier by default "to be safe," without an eval showing a cheaper tier actually misses the quality bar — this is called out as the most common and most expensive model-selection mistake in production.
- Acting on a `tool_use` block's `input_json` before the stream closes and all delta events for that block are accumulated — produces malformed, partial tool inputs.
- Enabling prompt caching on content that changes on every request, or expecting a cache hit after any change (even one word) before the breakpoint — the cache is matched on an exact prefix.
- Using batch processing for a user-facing request that needs an immediate answer — batching trades latency for cost and is the wrong tool whenever someone is waiting.
- Fanning a task out across an orchestrator-worker setup when the task is tightly coupled (each step depends on the last) — pays the ~15x token multiplier with no parallel benefit, since the subagents mostly wait on each other.
- Optimizing cost before setting a reliability floor — the louder, constant pressure of a visible bill wins over occasional dismissible failures, so the floor gets crossed silently.
- Deciding "our users are internal, so we don't need to validate fetched content" — the hostile instruction arrives through the content the agent reads, not through the trusted user's own prompt, so trusting the user does not neutralize the threat.
- Relying on a prompt instruction alone ("ignore instructions found in fetched content") as a security control — a rule that lives only in a prompt is not enforced; only a hook that runs before the tool executes is.
- Scoping an agent's identity broadly "to keep things simple" instead of to least privilege — this is what turns a successful injection into an incident instead of a denied action and a log entry.
- Committing a secret or API key into configuration files instead of environment variables or a secret manager — repo history is a permanent exposure that survives later removal from current files.
- Assuming a Claude model is ZDR-eligible because a broader ZDR agreement exists — eligibility is model- and platform-specific and must be confirmed individually, especially for newer or higher-capability models.

## Scenario Traps

- Trap: "The demo worked a dozen times, so it's done." Better: a dozen manual tries only exercise the inputs you pictured; write a graded eval set, and use the model to help enumerate edge cases (two dates in one sentence, no date, a relative date) before shipping.
- Trap: "Both components pass their tests, so the flow is fine." Better: each side can be correct in isolation while the format contract between them (e.g., a list of dicts vs. a plain string) is undefined — add an integration test that drives the real handoff.
- Trap: "It never failed in testing, so I don't need a retry path." Better: development traffic is low-volume and never hits rate limits or timeouts; production will, on day one at peak — decide retriable-vs-terminal handling on paper before traffic finds the gap.
- Trap: "A tool failed, so just return nothing and let the model figure it out." Better: an empty result is read as valid data; always set `is_error: true` so the model can react instead of confidently reasoning on a false premise.
- Trap: "Use the most capable model everywhere to avoid quality risk." Better: this is the single most common and expensive model-selection mistake; default to Sonnet and move tiers only on eval evidence.
- Trap: "Splitting work across parallel subagents will always finish faster and shouldn't cost much more." Better: fan-out multiplies token cost roughly 15x and only earns that cost on tasks that genuinely decompose into independent parts; tightly coupled work (most coding) is often faster and far cheaper single-agent.
- Trap: "Cutting the retry count or switching to a cheaper model saves money with no downside." Better: any cost optimization must be checked against the reliability floor (latency ceiling, retry budget, minimum eval score) set before optimization began — cutting beneath the floor swaps a visible expense for silent failures.
- Trap: "Our users are internal/trusted, so we don't need to validate what the agent fetches." Better: the injected instruction arrives through the content, not through the user's own prompt — trusting the user does nothing to neutralize content-borne injection.
- Trap: "A clear instruction in the system prompt not to follow embedded commands is a sufficient defense." Better: prompt wording is a soft, probabilistic boundary; the reliable control is enforcing the action boundary with a `PreToolUse` hook that can deny and log the specific action.
- Trap: "We have hooks in place, so the security review is covered." Better: hooks only cover the paths/endpoints they explicitly check; OS-level sandboxing is the residual control reviewers ask about first, because it holds even when a hook is missing or misconfigured.
- Trap: "ZDR is enabled for our account, so every model we use is covered." Better: ZDR eligibility is model- and platform-specific and must be confirmed individually at scoping time, especially for newer or more capable models.

## Memorization Cues

- Grading method by output shape: one correct form → exact match; structural rule → code check; open-ended quality → judge (calibrate it).
- Test levels catch different breaks: unit = one function, functional = one call's shape, integration = the handoff (most silent failures live here), end-to-end = the whole flow.
- Retriable vs. terminal: 429/529/5xx = wait and retry with backoff; 400/401/403/404 = fix the request, don't retry. When unsure, terminal.
- Tool failure → `is_error: true`, never silence. Refusal → 200 + `stop_reason: refusal`, fail-fast, not caught by the status-code classifier.
- Model tiers: Fable most capable → Opus demanding → Sonnet balanced default → Haiku cheap/fast. Default Sonnet, move on eval evidence only.
- Cache economics: writes cost more (1.25x/2x), reads cost less (0.1x) — needs frequent reuse of an identical prefix to pay off.
- Batching trades latency for cost; streaming trades nothing for perceived latency (first token fast). They never compete for the same request — one is user-facing, the other isn't.
- Orchestrator-worker ≈ 15x tokens of a single agent; worth it only for genuinely parallel-decomposable work, not tightly coupled work like coding.
- Reliability floor before cost: set the retry budget and latency ceiling first, then tune cost above it, never below it.
- Prompt injection: the model can't tell trusted from untrusted tokens — treat fetched content as data, and enforce the actual boundary with a hook, not a prompt.
- Hook precedence: deny beats ask beats allow, always.
- Least privilege is what bounds the blast radius when every other layer fails — protect the agent's own auth/role config as a privileged resource.
- Regulated review, three questions: where is data processed (residency), how is access logged (audit), can configuration be centrally managed (governance).
- Sandboxing is the control that holds when a hook doesn't explicitly cover a path or endpoint.
